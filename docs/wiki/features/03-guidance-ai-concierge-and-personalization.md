# Guidance, AI Concierge & Personalization

This is the **Prioritize → Explain → Recommend/Decide** stage of C2C's decision & action loop (see [Introduction](../00-introduction.md#the-decision--action-loop)) — the systems that decide *what a homeowner should do next* and *why*, primarily in service of Job 2 ("help me make the right home decision") but feeding Job 1's daily-attention feed as well. It spans the Ask concierge (an execution/orchestration system, not a raw chatbot), the Guidance Engine (per-issue repair/replace journeys), the canonical Home Actions/orchestration ranking pipeline with its "decision trace" trust mechanism, an explicit-consent personalization engine with progressive profiling, tool discovery/override, a published knowledge hub, and the Home Score → Property Brief lineage (Home Score is fully retired). This is also the cluster where C2C's trust architecture is most fully built out — the decision trace and personalization's context-map are the concrete answer to "why am I seeing this?" Everything below was verified against current route/controller/service/component code, not the historical FRDs in `docs/functional/` — several of those (`GUIDANCE_ENGINE_FRD*.md`, `AI_HOME_CONCIERGE_ASK_*.md`, `CAPABILITY_DISCOVERY*.md`) describe designs that are superseded, partially shipped, or aspirational relative to what is actually wired up today.

### Ask AI Concierge
- **What it does:** A guided, execution-based "Ask Cozy" workflow — not a freeform chatbot — that answers a homeowner's question, may ask an inline clarifying question or request a missing data capture, requires explicit confirmation before it writes anything (e.g. booking, escalation), and produces a session history the homeowner can revisit or delete. It also surfaces a "Concierge Home" and a "priority list" of home actions the user can give thumbs-up/down feedback on.
- **User flow:**
  1. Homeowner opens `/dashboard/ask` (or launches Ask from another surface via `launchSurface`/`launchCapabilityId` deep-link params).
  2. `AskWorkspace` loads Concierge Home (`GET /api/ask/concierge-home`) and recent/pending sessions.
  3. User types a question → `POST /api/ask/executions` creates an execution; the orchestrator may return a clarification request, an inline capture request (with a "use general estimate" or "open full form" fallback), a property-selection prompt (multi-property accounts), or a direct result.
  4. If the action is consequential, the user must explicitly confirm (`POST /api/ask/executions/:id/confirm`, idempotent, versioned against a `confirmationVersion` to catch stale context) before anything executes.
  5. User can request a correction, leave helpful/not-helpful feedback on the execution, or rate individual home-action items for usefulness; sessions can be resumed (`continue`) or deleted.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/ask/page.tsx` → `apps/frontend/src/components/ask/AskWorkspace.tsx` (~1700 lines: monitor cards, clarification/capture/confirmation UI, session list). Supporting logic in `apps/frontend/src/features/ask/` (`accountEligibility.ts`, `conciergeLandingPolicy.ts`, `presentationCompatibility.ts`).
- **Backend:** `apps/backend/src/routes/ask.routes.ts` mounts under `/api/ask/*` (executions, captures, clarifications, confirm, cancel, feedback, monitors, sessions) guarded by `authenticate` + `requireAskEligibleAccount`. Controller: `apps/backend/src/controllers/ask.controller.ts`. Orchestration logic: `apps/backend/src/services/ask/askOrchestrator.service.ts`. Account-level gating: `apps/backend/src/middleware/askAccountEligibility.middleware.ts` + `apps/backend/src/services/ask/askAccountEligibility.ts`. A separate `/api/ask/monitors/:id` pair actually proxies a **refinance rate monitor** (`RefinanceRateMonitor` service), reused inside the Ask surface rather than being Ask-specific.
- **Data:** `AskSession`, `AskExecution`, `AskExecutionEvent`, `AskTrustReviewCandidate`, `AskCaptureReceipt`, `AskConfirmationReceipt` (all in `apps/backend/prisma/schema.prisma`).
- **Notes:**
  - **This is a distinct system from `/api/gemini/chat`.** `gemini.routes.ts` exposes `POST /api/gemini/chat` (backed by `answerGroundedAsk`/`groundedAsk.service.ts`, using `GroundedAskProposal`/`GroundedAskArtifact` models) plus a propose/confirm/reject flow. The frontend API client defines `sendMessageToChat()` for this endpoint, but a repo-wide search found **no caller of it anywhere in the frontend** — the live Ask UI (`AskWorkspace.tsx`) talks exclusively to `/api/ask/*`. Treat `/api/gemini/chat` as either dead code or an unshipped alternate entry point; **not confirmed live** as a user-facing surface.
  - **`GEMINI_CHAT_ENABLED` (documented in `apps/CLAUDE.md` as "the backend runtime authority for AI chat") does not appear anywhere in `apps/backend/src/`.** It is stale documentation. What actually gates the Ask concierge today is a much more granular kill-switch system in `apps/backend/src/config/askOperationalControls.ts`: `ASK_ENABLED` / `ASK_KILL_SWITCH`, plus per-operation, per-consumer, per-domain, per-adapter, and per-context-provider `ASK_*_ENABLED` / `ASK_*_KILL_SWITCH` env pairs, and a separate `ASK_ACCOUNT_ROLE_ELIGIBILITY_ENABLED` flag enforced by `requireAskEligibleAccount` (returns 503 if disabled, 403 if the account role isn't eligible).
  - Gemini itself is invoked through `apps/backend/src/services/gemini.service.ts` (Google GenAI SDK, `GEMINI_API_KEY`, an in-memory chat-session cache with TTL/eviction, a circuit breaker (`AICircuitBreaker`) and timeout wrapper around calls). Ask-specific prompt minimization lives in `apps/backend/src/services/ask/askPromptMinimization.ts`.
  - Dependency failures degrade gracefully: `sendAskDependencyError()` in the controller maps `AI_TIMEOUT`/`AI_CIRCUIT_OPEN`/upstream errors to a 503 with a message that record-based Ask operations remain available, rather than a hard failure.
  - No decision-trace/explainability endpoint is specific to Ask executions; trust surfacing for Ask is via its own confirmation/version-conflict machinery, not the orchestration decision trace described below.

### Guidance Engine
- **What it does:** A per-issue (or per-service) step-by-step "journey" that walks a homeowner through resolving a problem with an inventory item or booking a service — e.g. diagnose → verify history → repair-vs-replace decision → model shortlist → vendor suggestions → booking handoff. It is explicitly issue-scoped (a `GuidanceJourney` tied to an `issueType` and optionally an `inventoryItemId`), not a general chat.
- **User flow:**
  1. From the property's Fix hub (`/dashboard/properties/[id]/fix`) or Resolution Hub, the user picks "Something's Broken" or a specific broken item and starts a journey (`POST /guidance/journeys/start`), which can also branch off a repair-vs-replace decision.
  2. The journey routes the user to `/dashboard/properties/[id]/tools/guidance-overview` (or the step-specific page under `.../guidance/step`), rendering the current step's inline component (coverage check, recall check, price check, verify-history with a 2-year lookback, replacement-priorities capture, capital-timeline step, do-nothing step, etc.).
  3. Each step can be completed, skipped (with a reason), or blocked (missing context); step completion can also come from a tool-completion event (`recordGuidanceToolCompletion`) when the user finishes an external tool (e.g. the model shortlist or vendor-suggestion generators).
  4. The user can change the issue type mid-journey, dismiss the journey, or resume it later; an "execution guard" endpoint checks whether the journey is ready for a target action (booking, claim escalation, inspection scheduling, provider handoff).
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/guidance-overview/` (`GuidanceOverviewClient.tsx`, `GuidedJourneyTemplate.tsx`, `GuidanceOverviewInlineStep.tsx`, `DismissConfirmPanel.tsx`) and `.../guidance/step/GuidanceStepPageClient.tsx`. Rich component library in `apps/frontend/src/components/guidance/` (~26 files: `GuidanceDrawer`, `GuidanceJourneyStrip`, `RepairReplaceGate`, `VerifyHistoryStep`, `RecallCheckInline`, `PriceCheckInline`/`PriceFinalizationInline`, `CoverageCheckInline`, `NegotiationShieldInline`, `ReplacementJourneyInline`, `CapitalTimelineGuidanceStep`, `DoNothingGuidanceStep`, `HomeSavingsGuidanceStep`, `OwnershipCostsGuidanceStep`, `ScopedWorkspaceGuidanceStep`). Hooks in `apps/frontend/src/features/guidance/hooks/` (`useGuidance`, `useJourney`, `useExecutionGuard`).
- **Backend:** `apps/backend/src/routes/guidance.routes.ts`, all under `/api/properties/:propertyId/guidance/*` (journeys list/detail/start/dismiss/change-issue/branch-from-repair-replace, next-step, execution-guard, signals/resolve, steps/:id/complete|skip|block, tool-completions, model-shortlist, vendor-suggestions, issue-types, service-categories, symptom-types, asset-resolution-context). Controller: `apps/backend/src/controllers/guidance.controller.ts` (~600 lines), delegating to `apps/backend/src/services/guidanceEngine/` (`guidanceJourney.service.ts`, `guidanceStepResolver.service.ts`, `guidanceBookingGuard.service.ts`, `guidanceTemplateRegistry.ts`, `modelShortlistAdvisor.service.ts`, `vendorSuggestionsAdvisor.service.ts`).
- **Data:** `GuidanceSignal`, `GuidanceJourney`, `GuidanceJourneyStep`, `GuidanceJourneyEvent`, `GuidanceStepEvidence`.
- **Notes:** Model-shortlist and vendor-suggestion generation (`generateGuidanceModelShortlist`, `generateGuidanceVendorSuggestions`) are Gemini-backed advisors scoped to a specific asset/budget/priority input, not general chat. The journey's "verify history" step pulls a 2-year lookback via `asset-resolution-context` (marked `FRD-FR-03` in code comments). Rate limiting (`apiRateLimiter`) applies to the whole router. No dedicated decision-trace endpoint exists for guidance journeys themselves — trust/explainability at this layer is mostly the step evidence trail (`GuidanceStepEvidence`) plus the `components/trust/` badges used inline (see Orchestration section).

### Orchestration, Next-Best-Action & Home Actions
- **What it does:** The canonical "what should this homeowner do next" ranking layer. It aggregates candidate actions from many sources (maintenance, coverage, incidents, guidance journeys, personalization, etc.), deduplicates and scores them, and exposes a single ranked feed plus a per-property summary used by the dashboard and the Fix hub. Users can mark an action complete (with optional completion data/photos), undo that, snooze/unsnooze an action, and — critically — **inspect a "decision trace" showing why an action was ranked/generated the way it was.**
- **User flow:**
  1. Dashboard and Fix hub load `GET /api/orchestration/summary/:propertyId` (or the canonical `GET /api/properties/:propertyId/home-actions` / `home` feed) to render ranked cards.
  2. User can open a card's decision trace (`DecisionTraceDrawer`/`DecisionTraceModal`/`DecisionTracePanel` in `components/orchestration/`) to see the reasoning.
  3. Completing an action can require a photo/completion form (`CompletionModal`, `PostSavePanel`) via the orchestration-completion sub-routes; completions sync back into `PropertyMaintenanceTask` status.
  4. Snoozing sets a `snoozeUntil` (capped at 365 days); unsnoozing brings the action back immediately.
  5. Marking complete/undo both write `OrchestrationActionEvent` rows and fire analytics/north-star lineage events, so the trace and audit trail stay consistent even after an undo.
- **Frontend:** `apps/frontend/src/components/orchestration/` (`OrchestrationActionCard.tsx`, `DecisionTraceDrawer.tsx`, `DecisionTracePanel.tsx`, `DecisionTraceItem.tsx`, `decisionTraceLabels.ts`, `ConfidenceBar.tsx`, `ConfidencePopover.tsx`, `CompletionModal.tsx`, `SnoozeModal.tsx`, `PropertyOrchestrationStrip.tsx`). Trust-badge primitives in `apps/frontend/src/components/trust/` (`ConfidenceBadge`, `TrustMetadataBar`, `WhyThisMattersCard`, `SourceChip`, `RiskOfDelayBadge`, `EstimatedSavingsBadge`) are used across orchestration, resolution-center, and guidance surfaces. The Fix hub (`apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/fix/page.tsx`) and the legacy `/dashboard/resolution-center` (now a deprecated redirect via `JobHubRedirectPage`) both consume this layer.
- **Backend:** `apps/backend/src/routes/orchestration.routes.ts` (`GET /summary/:propertyId`, `GET /summary/:propertyId/decision-diagnostics`, `POST /:propertyId/actions/mark-completed`, `POST /:propertyId/actions/:actionKey/undo|snooze|unsnooze`, **`GET /:propertyId/actions/:actionKey/trace`**) plus `orchestrationCompletion.routes.ts` (`GET`/`PUT /:propertyId/completions/:completionId`, photo upload/delete). Controllers: `orchestration.controller.ts`, `orchestrationCompletion.controller.ts`. Ranking/dedup/scoring logic and the canonical feed live in `apps/backend/src/services/homeActions.service.ts` (`rankAndDeduplicateHomeActions`, `scoreHomeAction`, `getHomeActionFeed`, `getUnifiedHome`, `executeHomeActionCommand` — a ~1400-line file); the summary itself is built in `apps/backend/src/services/orchestration.service.ts`.
- **Data:** `OrchestrationActionEvent`, `OrchestrationActionSnooze`, `OrchestrationActionCompletion`, `OrchestrationActionCompletionPhoto`, **`OrchestrationDecisionTrace`**, `HomeActionProactiveDeliveryDecision`.
- **Notes:** **The "decision trace" / trust architecture is real and live**, not aspirational: `getOrchestrationDecisionTraceHandler` reads a `OrchestrationDecisionTrace` row keyed on `(propertyId, actionKey)`, and the frontend has a dedicated drawer/modal/panel component set to render it, plus a whole `components/trust/` badge library (confidence, "why this matters," source chips, estimated savings, risk-of-delay). Completing/undoing an action two-way-syncs with `PropertyMaintenanceTask` status. `home-actions.routes.ts` (canonical feed: `/properties/:propertyId/home-actions`, `/home`, action commands, interactions) is a second, more modern entry point layered on the same `homeActions.service.ts` — the summary endpoint and the canonical feed endpoint are not the same route and it wasn't confirmed from code alone which one is the dashboard's primary data source vs. a newer parallel path; both are live and wired to controllers. **Flagging this as a product/implementation alignment issue, not a documentation gap:** the Job 1 "ranked attention feed" this wiki describes as one thing is, in the code, two parallel APIs over the same ranking logic — see [Introduction](../00-introduction.md#known-implementation-alignment-issues).

### Personalization Engine
- **What it does:** Produces at most three ranked, explainable home-improvement/safety suggestions per property, driven primarily by property-derived signals, with an **explicit-opt-in, minimal-collection household profile** ("progressive profiling") that only ever adjusts *ranking*, never eligibility or safety rules. Every suggestion carries a reason and a "why this home" fact; users can give feedback (not relevant / dismissed / complaint) and there's a transparency view ("context map") showing exactly what data fed the recommendation.
- **User flow:**
  1. `/dashboard/personalization` loads `GET /properties/:id/personalization`; if guidance is paused, only a profile-removal control is shown.
  2. If the household hasn't opted in, a card offers "Improve my recommendations" (`POST .../profile/enable`) with a note that family/health/income/pet details are never inferred.
  3. If enabled, at most one optional profile question is shown at a time (`nextQuestion`), answered via `POST .../questions/:questionId/answers` with Yes/No, integer, single-select, or multi-select controls, or skipped/snoozed.
  4. Up to three ranked recommendations render, each with a headline, "why" explanation, and (for at least one hardcoded case — smoke-detector review) an inline `PropertyContextCapturePanel` to confirm/correct a safety-relevant property fact before recomputing.
  5. User can give per-recommendation feedback (thumbs-down "not relevant" with a reason code, or "report a problem" free-text complaint), manually refresh, convert a recommendation to a task, or view the read-only "context map" (property signals vs. explicit profile facts vs. active recommendations) if their capability allows it, and can fully reset (delete) their optional profile at any time.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/personalization/page.tsx`. API wrapper: `apps/frontend/src/lib/api/personalizationApi.ts`.
- **Backend:** `apps/backend/src/routes/personalization.routes.ts`, mounted at `/api/properties/:propertyId/personalization/*` (root GET, `context-map`, `profile/enable`, `refresh`, `modules/:module/recommendations`, `questions/:questionId/answers`, `recommendations/:id/actions/convert-to-task`, `recommendations/:id/feedback`, `DELETE .../profile`). Every route is gated per-action by a **capability middleware** (`requirePersonalizationCapability`) with named capabilities (`canViewOrdinaryRecommendations`, `canViewSensitiveEvidence`, `canManageSensitiveProfile`, `canAct`, `canGiveFeedback`) — a finer-grained authorization model than most other routers in this cluster. Controller/module: `apps/backend/src/modules/personalization/api/personalization.controller.ts`. A separate `adminPersonalization.routes.ts` exists for admin-side management (not read in detail here).
- **Data:** `Household`, `HouseholdProperty`, `HouseholdMember`, `RecommendationDefinition`, `RecommendationRule`, `RecommendationContentVersion`, `PersonalizedRecommendation`, `RecommendationExplanation`, `RecommendationFeedback`, `RecommendationIncident`, `RecommendationSuppression`, `PersonalizationAuditEvent`, `PersonalizationEvaluationRun`, `RecommendationGovernanceReview`.
- **Notes:** This is one of the more mature, deliberately-designed pieces of the cluster — the UI text itself states the design intent ("Your optional answers changed the order, not the safety or eligibility rules") and the context-map view is a genuine, code-verified explainability surface (distinct from orchestration's decision trace). A `smoke_detector_installation_review` recommendation code is special-cased directly in the frontend with hardcoded copy, suggesting at least one safety-sensitive rule was hand-tuned post-launch. Capability governance for which rules can go live is reviewed via `releaseGate.routes.ts`'s `/capabilities/:capabilityId/governance-reviews` endpoint and `RecommendationGovernanceReview`/`CapabilityGovernanceReview` models.

### Tool Discovery, Capability Suggestions & Overrides
- **What it does:** A cross-cutting "canonical capability" catalog that (a) tells the frontend what tools/features exist and whether they're available to a given user/property, (b) contextually suggests the next 1-3 relevant tools/capabilities on a given surface (home, property, workflow, related-to-current, post-completion), and (c) lets a household tune numeric parameters ("tool overrides") that feed into calculators like the capital timeline or do-nothing simulator.
- **User flow:**
  1. `/dashboard/home-tools` (formerly `/dashboard/ai-tools`, which now permanently redirects there — "AI is an implementation detail, not a separate homeowner job," per an in-code comment) renders `ExploreToolsCatalog`, populated from the capability catalog and the unified-home context.
  2. Other surfaces (guidance steps, capability completions, orchestration cards) show `InlineCapabilitySuggestion`/`InlineCapabilitySuggestionSlot` — small "you might also want to..." prompts driven by `GET /properties/:id/capability-suggestions` with a source-lineage context (which action/journey/project triggered the suggestion).
  3. Completing a capability posts to `capability-completions/next` to resolve what to suggest immediately afterward (`PostCompletionCapabilityNextStep`), and completion/impression events are logged for lifecycle analytics (`tool-discovery/events`).
  4. Users (with contributor role) can adjust named numeric overrides for a property at `PUT /properties/:id/tool-overrides`.
- **Frontend:** `apps/frontend/src/features/tools/` (large: `ExploreToolsCatalog.tsx`, `capabilityCatalog.ts`, `capabilityApi.ts`, `CapabilityDiscoveryAnchor.tsx`, `InlineCapabilitySuggestion(.tsx/Slot.tsx)`, `PostCompletionCapabilityNextStep.tsx`, `toolDiscoveryRegistry.ts`, `useCapabilityCatalog.ts`, `useRelatedCapabilities.ts`, `useInlineCapabilitySuggestion.ts`, `toolLifecycleTelemetry.ts`, plus per-launch-context helpers for compliance/DIY/inspection-hub/project-tracker/seller-prep flows).
- **Backend:** `apps/backend/src/routes/toolDiscovery.routes.ts` (`GET /tool-capabilities`, `GET /tool-discovery/availability`, `POST /properties/:id/tool-discovery/events`), `apps/backend/src/routes/capabilitySuggestions.routes.ts` (`GET /properties/:id/capability-suggestions`, `POST .../capability-completions/next`, `POST .../capability-suggestions/feedback`, `GET .../related-capabilities`), `apps/backend/src/routes/toolOverride.routes.ts` (`GET`/`PUT /properties/:id/tool-overrides`). Registry: `apps/backend/src/productFramework/capabilities`. Services: `capabilityRecommendation.service.ts`, `capabilityRelated.service.ts`, `capabilityCompletion.service.ts`, `capabilityFeedback.service.ts`, `toolDiscoveryAvailability.service.ts`, `analytics/toolLifecycle.ts`.
- **Data:** `ToolOverride`; capability suggestions/completions/feedback appear to be computed/policy-driven rather than backed by dedicated persisted models found in this pass (not fully confirmed — the capability registry itself is largely code/config, not a DB table).
- **Notes:** The suggestions endpoint has a "smoke test" escape hatch (`x-capability-smoke-run` header + an IP/property allowlist in `smokeTestConfig`) that bypasses eligibility recording — useful for synthetic monitoring, worth knowing about if suggestion metrics look off. Release-readiness of individual capabilities is governed by `releaseGate.routes.ts` (`GET /api/admin/release-gates`, per-tool gate check, governance-review recording) — this is the release-gating equivalent of a feature flag, but scoped to capability rollout rather than a boolean env var.

### Knowledge Hub
- **What it does:** A public-ish (auth-optional for reading) library of published help articles, with property-targeted surfacing (articles relevant to a specific home's current state) and a separate authoring/admin workflow.
- **User flow:**

  2. In-app, property-targeted articles are fetched via `GET /properties/:id/knowledge/articles` (auth + property-auth required) so the list can reflect the property's context.

- **Frontend:** `apps/frontend/src/app/knowledge/{page.tsx,[slug]/page.tsx,layout.tsx,error.tsx,not-found.tsx}` (reads via `apps/frontend/src/lib/knowledge/api.ts`); admin at `apps/frontend/src/app/(dashboard)/dashboard/knowledge-admin/{page.tsx,new/page.tsx,[id]/page.tsx}`.

Controllers: `knowledgeHub.controller.ts`, `knowledgeHubAdmin.controller.ts`.
- **Data:** `KnowledgeArticle`, `KnowledgeArticleSection`, `KnowledgeArticleCategory`, `KnowledgeArticleTag`, `KnowledgeArticleToolLink`, `KnowledgeArticleCta`, `KnowledgeArticleRelation`, `KnowledgeArticleEvent`.
- **Notes:** A code comment in `knowledgeHubAdmin.routes.ts` explicitly flags that author/review/publish are **not yet separated** into distinct workflows ("that separation is Phase 4, per `ADMIN_MODULE_FRD.md` §10.6 — this endpoint set does both today") — a known, self-documented gap rather than something inferred.

### Home Score → Property Brief & Home Briefing (share links)
- **What it does:** The original "Composite Home Score" report/grade/trend/benchmark feature is **fully retired** and replaced by two live features: **Property Brief** (a purpose-built, shareable PDF-style brief with selectable sections/documents, used for things like a sale or refinance) and **Home Briefing** (a periodic, personalized digest of home-related items with per-item outcome tracking). Both support secure, revocable, time-limited public share links.
- **User flow (Property Brief):**
  1. From `/dashboard/properties/[id]/property-brief`, user picks a purpose/template, selects sections and eligible documents, and creates a brief (`POST .../property-briefs`).
  2. User previews it, republishes after underlying data changes (which detects `changedSectionTypes` and — if shares exist — queues an update-notice email), and creates a share (`POST .../property-briefs/:id/share`) with an expiry and download policy; a recipient can be emailed directly (fire-and-forget queue job) or given a copyable link.
  3. Recipients open `/property-brief/share/[token]` (no auth) to view, or hit a PDF download endpoint; the owner can revoke or test a share's access.
- **User flow (Home Briefing):** property view fetches `GET .../home-briefing`; homeowner can trigger generation, set delivery preferences, mark a delivery opened, record a per-item outcome, and create/revoke a selected share (`/home-briefing/share/[token]`, public).
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/property-brief/` (`PropertyBriefClient.tsx`, `propertyBriefApi.ts`) and public `apps/frontend/src/app/property-brief/share/[token]/page.tsx`; `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/home-briefing/` (`HomeBriefingClient.tsx`, `homeBriefingApi.ts`) and public `apps/frontend/src/app/home-briefing/share/[token]/page.tsx`. The old `.../properties/[id]/home-score/page.tsx` and `.../home-score/buyer-preview/page.tsx` are now pure `redirect()` shims into `property-brief`.
- **Backend:** Property Brief lives in the colocated module `apps/backend/src/propertyBrief/{propertyBrief.routes.ts,propertyBrief.service.ts,propertyBrief.contracts.ts}`, mounted at `/api/property-briefs/*` and `/api/properties/:id/property-briefs/*`. Home Briefing: `apps/backend/src/homeBriefing/{homeBriefing.routes.ts,homeBriefing.service.ts,homeBriefing.contracts.ts}`. **`homeScoreReport.routes.ts` and `homeScoreShare.routes.ts` are retired stubs**: every matched route now returns HTTP 410 with `code: 'HOME_SCORE_RETIRED'` / `'HOME_SCORE_SHARING_RETIRED'` / `'HOME_SCORE_PUBLIC_SHARE_RETIRED'` and a `replacement` pointer to `/api/properties/:id/property-briefs`. Similarly, `homeRiskReplay.routes.ts` retires the legacy `/risk-replay/*` endpoints (410, `LEGACY_RISK_REPLAY_RETIRED`) in favor of a reviewed `Past Hazard Exposure` source view (`/properties/:id/past-hazard-exposure`), gated by `requireReviewedIntelligenceCoverage('HOME_RISK_REPLAY')`.
- **Data:** `PropertyBrief`, `PropertyBriefSection`, `PropertyBriefEvidenceLink`, `PropertyBriefShare`, `PropertyBriefAccessLog`; `HomeBriefingPreference`, `HomeBriefingDelivery`, `HomeBriefingItem`, `HomeBriefingShare`, `HomeBriefingSharedItem`.
- **Notes:** This is a clean, well-documented deprecation — not a half-finished migration: both retirement stubs and the frontend redirects are consistent and the replacement path is advertised in the 410 response body itself. Property Brief's republish flow explicitly avoids re-notifying recipients unless something in the brief actually changed. Home Risk Replay's retirement is a related but separate deprecation (risk-history feature, not scored-report feature) worth not conflating with Home Score's.

### Do-Nothing Simulator, Home Capital Timeline & Narrative Reveal (supporting decision tools)
- **What it does:** Three smaller decision-support tools that plug into the above: the **Do-Nothing Simulator** projects the cost/risk of deferring maintenance/coverage decisions over a 6/12/24/36-month horizon under configurable assumption overrides (and can be launched from a specific guidance step); the **Home Capital Timeline** projects big-ticket replacement costs over time with user-overridable line items; **Narrative Reveal** is a one-time, AI-generated onboarding-style overlay shown on a property's page that nudges the user toward completing missing profile data.
- **User flow:** Do-Nothing: user creates/edits named scenarios and runs a simulation (`/dashboard/do-nothing-simulator` redirects, via `PropertyScopedToolRedirectPage`, to the property-scoped `.../tools/do-nothing`); results can be tied back to a guidance journey/step/signal. Capital Timeline: user views the latest run, triggers a re-run, and manages per-item overrides. Narrative Reveal: appears automatically on `/dashboard/properties/[id]` when an active `PropertyNarrativeRun` exists, animates in, offers a primary/secondary CTA (e.g. "See what's next for your home" / "Skip for now"), and can be dismissed or advanced by a patch call.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/do-nothing/DoNothingToolClient.tsx`; top-level `/dashboard/do-nothing-simulator/page.tsx` is a thin redirect wrapper. `apps/frontend/src/components/ai/DoNothingSimulatorPanel.tsx` and `apps/frontend/src/lib/api/doNothingSimulatorApi.ts`. Capital timeline is embedded as a guidance step component (`components/guidance/CapitalTimelineGuidanceStep.tsx`). Narrative: `apps/frontend/src/components/narrative/NarrativeRevealOverlay.tsx`, used from `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/page.tsx`.
- **Backend:** `apps/backend/src/routes/doNothingSimulator.routes.ts` (`/properties/:id/do-nothing/scenarios` CRUD, `/do-nothing/runs/latest`, `/do-nothing/run`) → `doNothingSimulator.controller.ts`. `apps/backend/src/routes/homeCapitalTimeline.routes.ts` (`/capital-timeline`, `/capital-timeline/run`, override CRUD) → `homeCapitalTimeline.controller.ts`. `apps/backend/src/routes/narrative.routes.ts` (`POST /properties/:id/narrative/run` to create-or-get a run, `PATCH /narrative/:runId` to advance/dismiss it).
- **Data:** `DoNothingScenario`, `DoNothingSimulationRun`; `HomeCapitalTimelineAnalysis`, `HomeCapitalTimelineItem`, `HomeCapitalTimelineOverride`; `PropertyNarrativeRun`.
- **Notes:** Do-Nothing's run endpoint explicitly accepts `guidanceJourneyId`/`guidanceStepKey`/`guidanceSignalIntentFamily`, confirming it's designed to be invoked *from inside* a Guidance Engine journey rather than only standalone. Narrative Reveal is a lightweight, single-shot AI nudge mechanism, separate from both the Ask concierge and the Guidance Engine — it was not fully traced end-to-end (its generation trigger/service was not read in this pass), so treat its content-generation path as **not confirmed** beyond the run/patch contract.
