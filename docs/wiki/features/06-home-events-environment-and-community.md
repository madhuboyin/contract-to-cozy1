# Home Events, Environment & Community

This page covers C2C's external/environmental awareness surface: the systems that watch the world outside the property line — severe weather, product recalls, environmental hazards, HOA rules, neighborhood change, and local community context — and surface it back to the homeowner. Most of these features are backed by a shared ingestion pattern (a BullMQ worker job polls a free/keyless government or public API on a cron schedule, normalizes the result, and either writes it straight to a property-scoped table or funnels it through the canonical **Home Event Radar** pipeline for matching, scoring, and notification). A few features here — HOA compliance, most notably — are pure user-entered record-keeping with no external feed at all. Where a section says "not confirmed live," it means the code path could not be found wired into a route, a scheduled job, or the frontend, even though a services file or Prisma model exists for it.

### Home Event Radar (hazard events)

- **What it does:** A unified, cross-hazard feed of events that could affect a specific property — severe weather alerts, earthquakes, FEMA disaster declarations, air-quality spikes, and more — each matched to the property, scored for relevance, and presented as a single chronological feed the homeowner can triage (seen/saved/dismissed/acted-on) and turn into a task.
- **User flow:**
  1. Homeowner opens **Home Event Radar** from the dashboard; the page resolves the active property and loads `/radar/overview` (coverage/readiness by category) and `/radar/feed`.
  2. Feed items are filterable by source family (Weather, Air Quality, Disaster, Utility, Tax, Insurance, Other) and by timing group (Needs attention / Upcoming / Recently ended).
  3. Tapping an item opens a detail sheet (`RadarDetailSheet`) with the full alert text; viewing it auto-marks the match `seen`.
  4. Homeowner can save, dismiss, or act on a match; "acting" can create or link a household task via the task-candidates/task endpoints.
  5. Homeowner can submit structured feedback on a match (e.g., "not relevant to me") and configure notification preferences (channels, categories, minimum severity/impact, quiet hours).
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/home-event-radar/{page.tsx,HomeEventRadarPageClient.tsx}`; `apps/frontend/src/components/features/homeEventRadar/{RadarFeedItem,RadarFeedSkeleton,RadarDetailSheet,RadarNotificationPreferences}.tsx`; deep-link/state helpers in `apps/frontend/src/features/homeEventRadar/`.
- **Backend:** Homeowner-facing (`apps/backend/src/routes/homeEventRadar.routes.ts`, controller `controllers/homeEventRadar.controller.ts`): `GET /properties/:propertyId/radar/{overview,coverage,counts,feed,events,preferences}`, `GET .../radar/matches/:matchId`, `PATCH .../radar/events/:matchId/state`, `POST .../radar/events/:matchId/feedback`, `GET/POST .../radar/events/:matchId/actions/:actionCode/{task-candidates,task}`, `POST .../radar/analytics-events`. Admin/operator surface (`homeEventRadarAdmin.routes.ts`, `homeEventRadarAdmin.controller.ts`, gated by ADMIN + MFA + `INTEGRATION_MANAGE` capability): source registry list/pause/test-fetch/run, run replay, event lineage, anomaly list.
- **Data:** `RadarSourceDefinition`, `RadarSourceHealth`, `RadarSourceCoverage`, `RadarSourceRun`, `RadarEvent`, `RadarEventRevision`, `PropertyRadarMatch`, `PropertyRadarCompoundInsight`, `PropertyRadarState`, `PropertyRadarAction`, `PropertyRadarTaskLink`, `PropertyRadarFeedback`, `PropertyRadarCoverage`, `PropertyRadarNotificationPreference`, `PropertyRadarNotificationDecision`.
- **Notes:** This is the canonical sink for several independent ingestion adapters in `apps/workers/src/radar/`: `nwsRadarAdapter` (severe weather, see below), `usgsEarthquakeRadarAdapter`, `openFemaDeclarationRadarAdapter`, `airNowRadarAdapter`, `freezeRadarAdapter`, plus QA-only `canonicalDummyRadarAdapter`/`dummyRadar.client.ts` (explicitly fenced off from production — the worker refuses to boot in `NODE_ENV=production` if `RADAR_DUMMY_INGEST_ENABLED` or `NEIGHBORHOOD_DUMMY_INGEST_ENABLED` is `true`, per a documented past incident where fake events leaked to prod). Each adapter's job (`severeWeatherAlerts.job.ts`, `ingestRadarSignals.job.ts`, an OpenFEMA job, an AirNow job) registers itself as a `RadarSourceDefinition`, begins a `RadarSourceRun`, and enqueues normalized observations onto a shared radar ingest queue for matching/dedup/lifecycle-convergence (an event can transition new → updated → resolved/expired/retracted as the upstream source's feed changes). A separate `radar-safety-net-reconciliation` cron job reconciles stuck/failed claims. Delivery is a further hop: `PropertyRadarNotificationDecision` rows (immediate or deferred per the user's quiet hours) are picked up by `apps/workers/src/runners/radarNotificationDelivery.poller.ts` and pushed onto email/push queues; `apps/workers/src/email/buildWeatherAlertCardHtml.ts` renders the email card. `homeEventRadarAdmin.routes.ts` is explicitly commented as a "temporary pre-canonical-ingestion operations surface" for QA/operator repair, not a stable provider API.

> **Naming trap:** `apps/backend/src/routes/homeEvents.routes.ts` (no "Radar" in the name) is a **different, unrelated feature** — a homeowner-authored property history/timeline log (`HomeEvent` model: repairs, incidents, claims, projects, each with evidence/verification/visibility, an annual recap, and CSV/PDF export via `GET .../home-events/annual-recap` and `POST .../home-events/export`). It belongs conceptually to Home Continuity & Records, not to this hazard-radar system — mentioned here only because the route file lives alongside `homeEventRadar.routes.ts` and is easy to confuse with it.

### Product Recalls

- **What it does:** Matches CPSC (U.S. Consumer Product Safety Commission) product recalls against a homeowner's inventory items, surfacing safety-relevant matches the homeowner can confirm, dismiss, or resolve.
- **User flow:**
  1. A worker job pulls new/updated recalls from CPSC and a separate matching job scans property inventory for matches.
  2. Homeowner sees matched recalls on the property (or a specific inventory item's) recalls list.
  3. Homeowner confirms a match (yes, I own this — routes into the guidance journey as a `recall_detected` safety signal), dismisses it (not applicable), or resolves it (records how it was addressed, e.g. replaced/repaired).
- **Frontend:** Not directly listed among the assigned frontend routes for this page; recalls surface inline on inventory item detail views (outside this page's scope — see inventory/onboarding-adjacent pages) and the same match records feed guidance journeys.
- **Backend:** `apps/backend/src/routes/recalls.routes.ts` → `controllers/recalls.controller.ts` → `services/recalls.service.ts`: `GET /properties/:propertyId/recalls`, `GET /properties/:propertyId/inventory/:itemId/recalls`, `POST .../recalls/matches/:matchId/{confirm,dismiss,resolve}` (each guarded by `recallMatchAuthMiddleware` in addition to property auth).
- **Data:** `RecallRecord`, `RecallProduct`, `RecallMatch`.
- **Notes:** Real external integration — `apps/workers/src/recalls/cpsc.client.ts` fetches from CPSC's public recall API (`ingestRecalls.job.ts` derives a severity from hazard/summary text: death/fatal → CRITICAL, fire/burn/electrocution/injury → HIGH, shock/choking/laceration → MEDIUM). Two BullMQ jobs run on a shared `RECALL_QUEUE_NAME`: `recall.ingest` (`recallIngest.job.ts`) and `recall.match` (`recallMatch.job.ts`, which also creates follow-up reminders for open matches via `recallFollowups.service.ts`). Confirming/dismissing/resolving a match also records a step completion in the guidance engine (`guidanceJourneyService.recordToolCompletion`) under the `recall_detected` signal family, so a confirmed recall can drive downstream guidance content.

### Severe Weather Alerts

- **What it does:** Live severe-weather warnings/watches (flash flood, tornado, severe thunderstorm, hurricane/tropical storm, excessive heat, winter storm/blizzard, red-flag fire-weather) for a property's location, sourced from the National Weather Service and delivered as Home Event Radar entries plus optional email/push notifications.
- **User flow:** Same consumption path as Home Event Radar above — a weather alert simply arrives as a `weather`-family radar event. There is no separate severe-weather screen; the homeowner controls delivery through the Radar notification-preferences card (channels, minimum severity, quiet hours, and a "critical safety override" that can bypass quiet hours for the most severe alerts).
- **Frontend:** Same as Home Event Radar (filter by the Weather category).
- **Backend:** `apps/backend/src/services/severeWeatherAlert.service.ts` (`SevereWeatherAlertService.getActiveAlerts(lat, lon)`) — no dedicated homeowner-facing route; it's consumed by the worker job below and by the incident evaluator (`services/incidents/`).
- **Data:** Flows into `RadarEvent`/`PropertyRadarMatch` (see above) and can also create rows in `Incident`/`IncidentEvent` via the incidents subsystem (`services/incidents/incident.service.ts`, `incident.evaluator.ts`).
- **Notes:** Real, live, keyless integration against `api.weather.gov/alerts/active` (point-radius query by lat/lon) — confirmed in `severeWeatherAlert.service.ts`. NWS event strings are mapped to internal hazard families (`FLOOD`, `STORM`, `HURRICANE`, `HEATWAVE`, `SNOW`, `WILDFIRE`); unmapped events (e.g. Air Quality Alert, Small Craft Advisory) are ignored by design. The worker job (`apps/workers/src/jobs/severeWeatherAlerts.job.ts`, registered as cron key `severe-weather-alerts`, source cadence `*/15 * * * *`) iterates every property with a geocoded location, fetches active alerts, dedupes by NWS alert ID (keeping the most-recently-sent version), and also runs a "lifecycle convergence" step (`apps/workers/src/radar/nwsLifecycleConvergence.ts`) that synthesizes resolution/expiry observations for alerts that silently drop out of the feed (a "stale safety net," gated on there having been no fetch failures, so a partial outage doesn't get misread as "all alerts resolved"). This is explicitly a **separate, more authoritative source** from `weather.service.ts`'s OpenWeatherMap-based freeze/heavy-rain heuristic used elsewhere for maintenance nudges (`GET /api/weather/check/:propertyId`) — the code comments in both files call this out directly to prevent the two from being conflated.

### Environment Report

- **What it does:** A property-level environmental briefing covering current/forecast weather, air quality, drought severity, flood zone & elevation, radon zone, nearby EPA-regulated facilities, and NOAA climate normals — each section independently sourced, cached, and marked ok/unavailable so one dead upstream API only degrades its own section.
- **User flow:**
  1. Homeowner opens Environment Report from a property (`/dashboard/properties/:id/environment-report`); the legacy **Climate** dashboard tab (`/dashboard/climate`) has been retired in favor of this — it now shows a banner ("Standalone climate scoring has been retired... insurance-premium ranges, or property-value predictions from unreviewed estimates") and links straight through.
  2. Report renders sourced current conditions, a 48-hour hourly outlook, a 10-day forecast, and 30-day history, plus the other sections below.
  3. For active weather insights (e.g. an upcoming freeze), homeowner can "start preparation" — generates a checklist (`WeatherPreparation` plan) they can track item-by-item (created/completed/canceled).
  4. Homeowner can also record HVAC filter maintenance directly from the report as maintenance context.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/climate/page.tsx` (redirect/deprecation shim) and `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/environment-report/` (primary surface, not fully enumerated here — file not read in depth for this page).
- **Backend:** `apps/backend/src/routes/environmentReport.routes.ts` → `controllers/environmentReport.controller.ts` → `services/environmentReport.service.ts` (report aggregation) + `services/environment/*.service.ts` (per-section fetchers): `GET /api/environment/report/:propertyId`, `POST .../maintenance-context`, `POST .../preparations`, `GET .../preparations/:id`, `PATCH .../preparations/:id/items/:itemId`.
- **Data:** Weather-prep plan/items persisted via `weatherPreparation.service.ts` (Prisma model not traced in depth here); property lat/lon/zip drive all section lookups.
- **Notes:** Every section is a real, live, mostly-keyless integration, not mocked — verified from source-file header comments: **weather** (Open-Meteo forecast + archive APIs, distinct from the OWM-based `weather.service.ts`), **air quality** (Open-Meteo Air Quality API), **drought** (US Drought Monitor `usdmdataservices.unl.edu`, weekly-published), **flood zone + elevation** (FEMA National Flood Hazard Layer ArcGIS REST + USGS Elevation Point Query Service — the code notes the old `hazards.fema.gov` host 404s and documents the replacement host found during implementation), **radon zone** (EPA's live ArcGIS radon-zone service, chosen over a static/transcribed county table for trustworthiness), **environmental hazards** (EPA ECHO unified facility search across RCRA/CAA/CWA/SDWA/TRI programs — Superfund/CERCLIS proximity search is explicitly **not** integrated, a documented scope gap), **climate normals** (NOAA NCEI 1991–2020 Climate Normals via CDO Web API v2, requires a free `NOAA_NCEI_TOKEN`; frost-date normals are explicitly left null — a documented known gap rather than a guess), and **hardiness zone** (USDA zone via the free `phzmapi.org` mirror, used by the Plant Advisor feature). All sections use `assertSafeUrl` (SSRF guard) and short fetch timeouts, and cache aggressively (30 min for fast-changing data up to 30 days for hardiness zone).

### HOA Compliance Tracking

- **What it does:** Lets a homeowner record their HOA/association's contact and dues info, track approval-record requests for home projects (submitted/approved/denied), and log violation notices — a pure record-keeping tool, not an automated compliance checker.
- **User flow:**
  1. Homeowner opens **HOA Compliance** for a property and enters association details (name, management company, contact info, dues amount/frequency) via `HoaAssociationCard`.
  2. Homeowner adds approval records per planned project (work type, status) via `ApprovalRecordList`, and can edit/delete them.
  3. Homeowner reports a violation via `ReportViolationModal`; violations appear in `ViolationHistoryList`.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/hoa/page.tsx`; `apps/frontend/src/components/features/hoa/{HoaAssociationCard,ApprovalRecordList,ReportViolationModal,ViolationHistoryList}.tsx`.
- **Backend:** `apps/backend/src/routes/hoaCompliance.routes.ts` → `controllers/hoaCompliance.controller.ts` → `services/hoaCompliance.service.ts`: `GET/PUT /properties/:propertyId/hoa`, `GET/POST /properties/:propertyId/hoa/approvals`, `PATCH/DELETE .../hoa/approvals/:id`, `GET/POST /properties/:propertyId/hoa/violations`.
- **Data:** `HoaAssociation`, `HoaApprovalRecord`, `HoaApprovalDocumentReview`; violations are persisted as `Incident` rows (reportViolation creates an `Incident`, per the controller).
- **Notes:** No external HOA data source exists or is implied — this is entirely homeowner-entered. The page itself is explicit about this: "Record-tracking only. Verify approval requirements with your association." Creating an approval record is gated behind a property-context completeness check (`evaluateFeatureContext`/`assertProjectComplianceDecisionsApplicable`) that can 409 with `PROPERTY_CONTEXT_INCOMPLETE` if required property responsibility data isn't filled in yet — a cross-feature dependency on the onboarding/property-setup flow. Reporting a violation also emits an `Incident`, tying HOA violations into the same incident-lifecycle machinery used elsewhere (acknowledge/status/suppression rules).

### Neighborhood Trust & Providers

- **What it does:** A zip-code-scoped trust layer distinct from hazard radar: shows headline neighborhood stats, a local activity feed, and top-rated service providers in the homeowner's area, plus lets homeowners endorse a provider after a completed booking (visible to neighbors, optionally anonymous).
- **User flow:**
  1. Homeowner opens **Neighbourhood Trust**; the page resolves their zip code from their property (`getHomeownerZipInfo`) and loads stats + a `contractors`/`feed` tab.
  2. Contractors tab: top providers by category in-zip, with star ratings and endorsement-tag badges (Quality work, On time, Fair price, Clean site, Clear comms, Honest estimate).
  3. Feed tab: recent neighborhood activity entries.
  4. After a completed booking, homeowner can submit an endorsement (would-hire-again + highlight tags, anonymous-to-neighbors by default) via a modal; can also view their own existing endorsement for a booking.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/neighbourhood-trust/page.tsx`.
- **Backend:** `apps/backend/src/routes/neighbourhoodTrust.routes.ts` → `controllers/neighbourhoodTrust.controller.ts` → `services/neighbourhoodTrust.service.ts`: `GET /neighbourhood/zip-info`, `GET /neighbourhood/feed`, `GET /neighbourhood/providers`, `POST/GET /bookings/:bookingId/endorse(ment)`.
- **Data:** `NeighbourhoodTrustProfile`, `NeighbourhoodEndorsement`, `NeighbourhoodFeedEntry`.
- **Notes:** This is a separate system from the "Neighborhood Intelligence" hazard/change-detection engine below despite the similar name — Neighbourhood Trust is built from C2C's own booking/endorsement activity (in-platform social proof), not an external feed. Endorsement submission also emits an analytics `ACTION_COMPLETED` event under the `COMMUNITY` module.

### Neighborhood Intelligence / "Around Your Home"

- **What it does:** Detects and interprets meaningful nearby changes (permits, zoning, land-use, infrastructure, school-district, flood-map revisions) that could affect a property's value or livability, presented as a sentiment-scored, themed summary ("Neighborhood Change Radar").
- **User flow:** Homeowner would view a summary card (meaningful-change count, sentiment, top themes) and drill into individual nearby events with impact/demographic detail, plus a trends view — **however, this legacy read surface's live status is unclear** (see Notes); the actively-developed successor is the "Around Your Home" panel exposed at `GET /properties/:propertyId/around-your-home`, which lists reviewed source-backed observations per property with per-source coverage/freshness state (`CURRENT`/`DEGRADED`/`STALE`/`UNAVAILABLE`/`NOT_CONFIGURED`) and lets the homeowner mark an item's interaction (e.g. dismiss/save).
- **Frontend:** Not confirmed live as a homeowner-facing page in this cluster's assigned directories — likely surfaces as a widget elsewhere (e.g. property dashboard/property-brief); the only frontend file directly found for this system is the fixture-gated QA harness `apps/frontend/src/app/acceptance/property-intelligence/` (`page.tsx` 404s unless `PROPERTY_INTELLIGENCE_ACCEPTANCE_FIXTURE=1`), which is not a real user flow.
- **Backend (legacy, mostly retired):** `apps/backend/src/neighborhoodIntelligence/neighborhoodIntelligence.routes.ts` still serves read endpoints — `GET /properties/:propertyId/neighborhood-radar/{summary,events,events/:eventId,trends,signals}` — but the **write/recompute/ingest endpoints on this router now return HTTP 410 Gone** with explicit messages like `LEGACY_NEIGHBORHOOD_RECOMPUTE_RETIRED` ("Manual radar recompute is retired... updates only when a reviewed source publishes a new or materially revised record") and `LEGACY_NEIGHBORHOOD_INGEST_RETIRED` ("Use the reviewed property-intelligence source ingestion API").
- **Backend (current):** `apps/backend/src/propertyIntelligence/propertyIntelligence.routes.ts` (`aroundYourHome.service.ts`, `propertyIntelligence.service.ts`, `governance.service.ts`): `GET /properties/:propertyId/around-your-home`, `POST .../around-your-home/:propertyMatchId/interaction`, `GET .../intelligence/{coverage,observations}`, plus an extensive ADMIN+MFA-gated console for managing intelligence sources, coverage, and governance (`/admin/property-intelligence/...`, `/admin/around-your-home/quality`).
- **Data:** Legacy: `NeighborhoodEvent`, `PropertyNeighborhoodEvent`, `NeighborhoodImpact`, `NeighborhoodScanJob`. Current: intelligence-source/coverage/observation tables under the `propertyIntelligence` domain (not enumerated in depth here — this feature is only briefly covered per the assigned scope; see the onboarding/property-setup page for the property-context plumbing it depends on).
- **Notes:** `apps/workers/src/worker.ts` still schedules `neighborhood-change-notifications` and `neighborhood-radar-refresh` (legacy pipeline) alongside newer source-specific jobs like `nyc-zap-planning-ingest` and `usgs-hazard-intelligence-ingest` (current pipeline) — so both systems' worker jobs coexist, even though the legacy router's write paths are stubbed out. A QA-only `ingestNeighborhoodDummyEventsJob` exists behind `NEIGHBORHOOD_DUMMY_INGEST_ENABLED`, with the same production guardrail described under Home Event Radar. Given the 410 stubs and the fixture-gated frontend, treat the legacy "Neighborhood Change Radar" summary/events/trends endpoints as **planned for replacement, not a confirmed live user-facing flow** — "Around Your Home" is the system actively being built out (visible from the depth of its admin governance tooling).

### Local Updates Feed

- **What it does:** A small (max 3), ranked carousel of location/dwelling-targeted informational or promotional cards (e.g. internet, insurance, maintenance, energy offers) shown to homeowners, with at most one sponsored card per view and per-user dismissal.
- **User flow:** Card(s) appear inline on the dashboard (as a carousel or a compact "ticker" variant); homeowner can tap through (CTA) or dismiss a card, which suppresses it for 30 days.
- **Frontend:** `apps/frontend/src/components/localUpdates/LocalUpdatesCarousel.tsx` (+ `LocalUpdateCard.tsx`, `localUpdates.types.ts`), rendered from `apps/frontend/src/app/(dashboard)/dashboard/page.tsx` and `apps/frontend/src/components/home/UnifiedHomeSurface.tsx`.
- **Backend:** `apps/backend/src/localUpdates/localUpdates.routes.ts` → `localUpdates.controller.ts` → `localUpdates.service.ts`: `GET /api/local-updates/:propertyId`, `POST /api/local-updates/:id/dismiss`.
- **Data:** `LocalUpdate`, `UserLocalUpdateDismissal`, `LocalUpdateEvent`.
- **Notes:** Ranking is deterministic and computed in-request (zip match +40, city match +25, dwelling-type match +15, owner baseline +10, recency bonus up to +20 for ≤7 days old, sponsored penalty −15, plus `priority * 2`) with a hard cap of one sponsored card. **Gap found:** no code path anywhere in `apps/backend` or `apps/workers` creates or upserts `LocalUpdate` rows — no admin route, no seed script, no ingestion job. This table appears to be populated by direct DB writes outside the application (e.g. manually or via an external CMS/process not in this repo), which is worth flagging to product/ops if that's not intended.

### Community Events, Trash & Local Alerts

- **What it does:** Surfaces nearby ticketed community events, municipal trash/recycling pickup info (including an AI-parsed schedule), and city emergency/announcement alerts, scoped to the property's city/state.
- **User flow:**
  1. Homeowner opens **Community** (`/dashboard/community-events`); page resolves the active property and defaults to an "Events" tab, with "Trash" and "Alerts" tabs alongside.
  2. Events tab lists nearby ticketed events (title, time, external ticket link) sourced from Ticketmaster.
  3. Trash tab shows municipal collection info for supported cities (RSS-sourced) plus an AI-parsed schedule summary.
  4. Alerts tab shows city-level emergency/announcement feeds (RSS, or NYC Open Data's emergency-notifications dataset where applicable).
  5. A compact version of the events list (`CommunityEventsCard`) also appears on the main dashboard with a "View all" link through to the full page.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/community-events/page.tsx`; `apps/frontend/src/components/{CommunityEventsCard,CommunityEventsList}.tsx`.
- **Backend:** `apps/backend/src/community/community.routes.ts` → `community.controller.ts` → `community.service.ts`: `GET /api/v1/community/events` (city-based) and `GET /api/v1/properties/:propertyId/community/events` (property-based), `GET /api/community/{trash,trash-schedule,alerts}` (on-the-fly, no DB writes), plus legacy `GET /api/v1/community/{trash,alerts}`.
- **Data:** No dedicated persistence found for events/trash/alerts themselves — this service is a live-fetch-and-cache layer (in-memory `Map`-based TTL cache per service instance; no DB model backing the on-the-fly responses).
- **Notes:** Real integrations, city-coverage-limited: **events** via Ticketmaster's public API (`providers/ticketmaster.provider.ts`, deduped by an event key, 5-min cache); **trash/alerts** via per-city RSS feed configuration (`providers/citySources.onTheFly.ts` resolves a "city key" and looks up configured RSS sources — unsupported cities degrade gracefully to an empty list rather than erroring, per an explicit try/catch); **alerts** additionally supports NYC Open Data's emergency-notifications dataset (`providers/nycOpenData.provider.ts`, optional `NYC_OPEN_DATA_APP_TOKEN`); **trash schedule** is parsed from source text via Gemini (`providers/trashSchedule.provider.ts`, `parseTrashScheduleWithAI`), cached for 24h. Because city coverage is a hand-maintained source list, this feature's real-world coverage is likely limited to a handful of pre-configured cities — not nationwide.

### Emergency Troubleshooting Help

- **What it does:** A stateless AI chat that triages a described home emergency (e.g. "toilet won't stop running," "I smell gas") and returns a severity/classification, a DIY-vs-call-pro-vs-immediate-danger resolution, and concrete first steps.
- **User flow:**
  1. Homeowner opens **Emergency** and describes their issue in a chat box.
  2. Each turn sends the full conversation history plus optional property context (structure/systems/safety scopes) to the backend.
  3. Response renders severity/resolution badges, a confidence percentage, and a numbered immediate-steps list; a persistent disclaimer reminds the user to call 911 for life-threatening emergencies.
  4. Conversation continues turn-by-turn (stateless on the backend — full history resent each time) until resolved.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/emergency/page.tsx`; `apps/frontend/src/components/EmergencyTroubleshooter.tsx`.
- **Backend:** `apps/backend/src/routes/emergency.routes.ts` → `services/emergencyTroubleshooter.service.ts`: `POST /api/emergency/chat`.
- **Data:** Best-effort logs each chat turn as an `Incident` (`typeKey: 'EMERGENCY_CHAT'`, `sourceType: MANUAL`) when both `userId` and `propertyId` are available — logging failure doesn't fail the chat response.
- **Notes:** Real AI integration via Google Gemini (`gemini-2.0-flash`, `GEMINI_API_KEY`, temperature 0.3, structured-JSON system prompt) — not mocked. The system prompt hardcodes specific safety rules (gas smell → evacuate + call gas company from outside; electrical sparking → turn off main breaker + call electrician; major water leak → shut off main water valve; sewage backup → don't use plumbing; never DIY for gas lines/electrical panels/structural issues) and forces `IMMEDIATE_DANGER` resolution for life-safety risk categories. When a `propertyId` is supplied, property context is pulled via `getPropertyContext` (CORE/STRUCTURE/SYSTEMS/SAFETY scopes) and run through an `evaluateEmergencyContext`/`applicabilityPolicy` step before being injected into the first message — a 404 is returned if the user doesn't have access to that property (`PropertyContextAccessDeniedError`).

### Property Intelligence & Property Brief (cross-reference only)

Two related systems live in this cluster's assigned backend directories but are primarily owned by the onboarding/property-setup domain, so they're only noted briefly here — see [Onboarding & Property Setup](01-onboarding-and-property-setup.md) for full coverage:

- **`apps/backend/src/propertyIntelligence/`** — the reviewed-source intelligence coverage/observation/governance framework that "Around Your Home" (above) is built on top of; it is property-level infrastructure shared across features, not neighborhood-specific on its own.
- **`apps/backend/src/propertyBrief/`** (`propertyBrief.routes.ts`, `.service.ts`) and its frontend at `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/property-brief/` plus the public share view `apps/frontend/src/app/property-brief/share/[token]/page.tsx` — a shareable PDF/report generator (`renderPropertyBriefPdf`, share-link creation/revocation/republish) that packages property facts for external sharing (e.g. with a buyer or agent). This is a document/reporting feature, not an environmental-awareness one, and belongs conceptually with onboarding/property setup or the sale/buyer transition flow.
