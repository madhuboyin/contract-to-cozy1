# Sale, Buyer & Life Transitions

This cluster is C2C's **Job 3** ("guide me through something major") — the life-event moments that happen around, rather than during, steady-state home ownership: deciding whether to sell/hold/rent, prepping and tracking a sale, buying and closing on a new home, moving logistics, refinancing a mortgage, and recording end-of-life/emergency household information. Each of these workspaces effectively runs its own version of the understand → identify → explain → execute → record loop scoped to the transition (e.g. Sale Readiness computes what's actually blocking a clean sale from real records, then tracks it to resolution). Most of these tools are property-scoped (`propertyAuthMiddleware` + a `PropertyId` in the URL) and several project their state from other canonical records (inspections, projects, permits, documents) rather than storing a self-reported checklist — a deliberate design choice called out repeatedly in the backend comments (see `propertySaleCase.service.ts`).

### Sale Readiness / Sale Case (property sale checklist)
- **What it does:** Gives a homeowner preparing to sell a single governed view of what stands between the property and a clean sale — safety/structural issues, permits/disclosure gaps, financial decisions, and cosmetic presentation items — computed from the property's real inspection findings, open projects, permit flags, and Home Actions rather than a self-reported percentage. It also tracks the sale timeline (list/close target dates, status LISTED → UNDER_CONTRACT → CLOSED/CANCELLED) and an ownership-transition record for handing curated property history to a buyer.
- **User flow:**
  1. Homeowner opens a property and navigates to the Sale Readiness tool (`/dashboard/properties/[id]/tools/sale-case`).
  2. If no sale case exists yet, they see a "Start a sale case" prompt; creating one requires `CONTRIBUTOR` household role.
  3. The page projects readiness items into groups by requirement class (material blockers, verification needed, professional decisions, optional improvements) plus a "Maximize your return" presentation section with cost/value-add estimates for cosmetic items.
  4. Homeowner can waive/reopen/pursue/unpursue individual items, set a prep budget range, and confirm "notable upgrades" surfaced from project/material/event records.
  5. When ready, they set target list/close dates and transition status; at close, they record a `PropertyTransition` (seller retention decision for private vs. shared history, and which `PropertyBriefShare`s to revoke).
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/sale-case/SaleCaseClient.tsx`, `MaximizeReturnSection.tsx`. Linked from `PropertyOwnershipResponsibilitySection` and the mobile tool catalog.
- **Backend:** `apps/backend/src/routes/propertySaleCase.routes.ts`, mounted at `/api` → all under `/api/properties/:propertyId/sale-case`. Key endpoints: `GET /` (get/compute case), `POST /` (create), `PATCH /dates`, `PATCH /status`, `PATCH /items/:itemId` (WAIVE/REOPEN/PURSUE/UNPURSUE), `POST /transitions`, `PATCH /transitions/:transitionId`, `POST /transitions/:transitionId/complete`, `GET /entry-flow`, `GET /prep-questions`, `PATCH /budget`, `GET /notable-upgrades`, `POST /notable-upgrades/confirm`. Logic in `apps/backend/src/services/propertySaleCase.service.ts` (1,500+ lines) — projects items live from `InspectionFinding`, `ProjectRecord`, `PropertyPermitRecord`/`PermitUnpermittedFlag`, `HomeEvent`, `MaterialSpec`, `Warranty`, `InventoryItem`, `PropertyMaintenanceTask`, and Home Actions.
- **Data:** `PropertySaleCase`, `SaleReadinessItem`, `PropertyTransition`, `PropertySalePrepProfile`, plus read-only joins into `InspectionFinding`, `ProjectRecord`, `PropertyPermitRecord`, `PermitUnpermittedFlag`, `HomeEvent`, `MaterialSpec`, `Warranty`, `InventoryItem`, `PropertyMaintenanceTask`, `PropertyBriefShare`.
- **Notes:** Requires household role `CONTRIBUTOR` for writes; reads allowed for any property-authorized user. This is the successor to the old `SellerPrepPlan.items` static checklist — that model's items were "retired" per code comments in `sellerPrep.service.ts` and the underlying `SellerPrepPlanItem` model was dropped from the schema entirely (confirms the memory note "Drop confirmed-dead SellerPrepPlanItem"). Reachable via real navigation, not just acceptance tests.

### Seller Prep (comparables, agent interviews, leads)
- **What it does:** A companion tool to Sale Readiness focused on market context and go-to-market help for a seller: nearby comparable listings, a readiness report, an agent-interview comparison guide, and a lead-capture flow to request provider/agent outreach. Requires the property to have confirmed sale intent (`Property.propertyUse === 'FOR_SALE'`) before a plan is created.
- **User flow:**
  1. From the property page or the Sale Case screen ("Talk to a listing agent" style CTA), homeowner opens `/dashboard/properties/[id]/seller-prep`.
  2. Sees an overview: sale-intent gate, comparables, a readiness report, and any saved agent interviews.
  3. Can add/compare agent interviews, delete one, save selling preferences, and submit a lead capture request (routed to providers).
- **Frontend:** `apps/frontend/src/components/seller-prep/SellerPrepOverview.tsx`, `SellerPrepCTA.tsx`, `SellerPrepDashboardCard.tsx`, `SellerPrepEntryFlowGate.tsx`, `AgentInterviewGuide.tsx`, `LeadCaptureModal.tsx`. Links target `/dashboard/properties/${propertyId}/seller-prep`.
- **Backend:** `apps/backend/src/sellerPrep/sellerPrep.routes.ts`, mounted at `/api/seller-prep`. Endpoints: `GET /overview/:propertyId`, `GET /comparables/:propertyId`, `GET /report/:propertyId`, `POST /lead/:propertyId` (requires `CONTRIBUTOR`), `POST /preferences/:propertyId`, `GET /preferences/:propertyId`, `POST /feedback`, `DELETE /agent-interview/:interviewId`. Logic in `sellerPrep.service.ts`, `providers/compsResolver.ts`, `reports/sellerReadiness.builder.ts`, `monetization/lead.controller.ts`.
- **Data:** `SellerPrepPlan`, `AgentInterview`, `SellerPrepLead`. (The old `SellerPrepPlan.items` checklist field is now always returned empty — see Sale Readiness above.)
- **Notes:** I could not find a top-level nav-catalog entry for `/dashboard/properties/[id]/seller-prep` itself (only cross-links from Sale Case, the Seller Prep CTA card, and the mobile tool catalog's `hrefSuffix: 'seller-prep'`), but those cross-links are real production code paths, not acceptance-only — this is reachable, just not a primary sidebar destination in its own right.

### Sell-Hold-Rent Decision Tool
- **What it does:** A financial calculator that projects 5- or 10-year net outcomes for selling now, holding, or renting out the property, using the property's real financial context (home value, mortgage, taxes, insurance) with optional user overrides for each assumption (appreciation rate, selling costs, rent growth, vacancy, management fee, etc.).
- **User flow:**
  1. Homeowner opens `/dashboard/properties/[id]/tools/sell-hold-rent` (reachable from the sidebar tools list, the mobile tool catalog, and the Capital Timeline tool). **Correction:** this page previously also credited "the Property Orchestration strip which chains it to/from Break-Even" as a reachable path — a frontend nav audit found `PropertyOrchestrationStrip.tsx` has zero importers anywhere in the frontend; it's dead code, not a real cross-tool chaining surface. See [Introduction](../00-introduction.md#known-implementation-alignment-issues).
  2. Picks a 5 or 10-year horizon.
  3. Reviews the computed comparison (sell vs. hold vs. rent) rendered as comparison bars; can adjust assumption overrides which re-run the calculation client-side against the API.
  4. Can save/name an assumption set for reuse.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/sell-hold-rent/SellHoldRentClient.tsx`, `ComparisonBars.tsx`, `sellHoldRentApi.ts`.
- **Backend:** `GET /api/properties/:propertyId/tools/sell-hold-rent` (query params for years + all assumption overrides), defined in `apps/backend/src/routes/sellHoldRent.routes.ts`, gated by `authenticate` + `restrictToHomeowner` + `propertyAuthMiddleware`. Controller `apps/backend/src/controllers/sellHoldRent.controller.ts`, service `apps/backend/src/services/sellHoldRent.service.ts`. Emits a `TOOL_USED` analytics event (`AnalyticsFeature.SELL_HOLD_RENT`).
- **Data:** Reads from the property's financial context envelope (`getCurrentFinancialContextEnvelope`) rather than owning a dedicated model of its own; no dedicated Prisma model for saved runs was found in this controller (assumption sets are passed as an `assumptionSetId` query param, likely resolved elsewhere in the financial-context service — not traced further here).
- **Notes:** `restrictToHomeowner` means this is homeowner-role only (not open to PROVIDER accounts). Response envelope is unusual — `{ success, data: { sellHoldRent: {...} } }`, and the frontend API wrapper (`sellHoldRentApi.ts`) has defensive fallback parsing for alternate shapes, suggesting this contract has shifted before. Fully wired into real navigation (sidebar dynamic actions, mobile catalog) — not an acceptance-only feature. (A prior version of this line also credited "the orchestration strip" as a live navigation path here; that's the same dead `PropertyOrchestrationStrip.tsx` corrected above and elsewhere in the wiki.)

### Home Buyer Task Tracking / Closing Plan
- **What it does:** A full closing-to-move-in workspace for a property in the buying lifecycle: a 90-day plan broken into phases (Contract, Financing & Protection, Due Diligence/Inspection, Closing Prep, Close & Move-in), covering purchase financing/lender readiness, Loan Estimate comparison, contract contingencies, title/escrow, homeowners insurance, final walkthrough, closing disclosure & funds readiness, and closing day. At day 91 (or on explicit confirmation), unresolved pre-close items "hand off" into the recurring Home ownership plan.
- **User flow:**
  1. Buyer opens `/dashboard/properties/[id]/buyer-plan` (linked from the main dashboard for buyer-stage properties, and reachable via `PropertyRecordOverview`/tool catalogs).
  2. Overview panel shows current stage, target close date, milestones, and the single recommended next action; personalization gate ("make this plan fit my home") runs first if incomplete.
  3. Buyer clicks into a workspace tab (Contract / Financing & Protection / Due Diligence / Closing Prep / Close & Move-in) to work specific tasks: confirm cash vs. financed purchase path, upload/extract Loan Estimates (OCR via multer + rate-limited endpoint), track lender conditions, manage contract-contingency revisions, title/escrow issues, insurance quotes/binding, final walkthrough observations/issues, closing-disclosure revisions and funds readiness, and closing-day confirmation.
  4. Inspection findings can be dispositioned as verified fact / negotiate pre-close (opens a Negotiation Shield case) / add to ownership plan / dismissed.
  5. Buyer can pause/resume/cancel the purchase journey; on reaching day 91 or explicit professional-close confirmation, unresolved tasks hand off into the recurring Home task feed.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/buyer-plan/page.tsx` (large client orchestrator, ~700 lines) plus per-domain center components in the same folder: `BuyerPurchaseLoanEstimateCenter.tsx`, `BuyerPurchaseLenderReadinessCenter.tsx`, `BuyerContractContingencyCenter.tsx`, `BuyerTitleEscrowCenter.tsx`, `BuyerInsuranceCenter.tsx`, `BuyerWalkthroughCenter.tsx`, `BuyerClosingDisclosureCenter.tsx`, `BuyerClosingDayCenter.tsx`, `BuyerInspectionGuide.tsx`, `BuyerPlanPersonalization.tsx`, `BuyerPlanExperience.tsx` (workspace/phase mapping), `BuyerWorkspaceGuidance.tsx`. Also `components/home/BuyerClosingHome.tsx` and `components/tasks/HomeBuyerChecklist.tsx` for dashboard-level summaries.
- **Backend:** `apps/backend/src/routes/homeBuyerTask.routes.ts`, mounted at `/api/home-buyer-tasks`. Very large surface (~40 routes) including: `GET /properties/:propertyId/closing-home`, `/overview`, `/checklist`, `/tasks`, `/stats`, `/import-readiness`, `/evidence-review`; `GET`/`PUT /inspection-plan`; `GET`/`PUT /purchase-financing` plus `/purchase-financing/loan-estimates` (list/create/extract/select/confirm) and `/purchase-financing/readiness`; `GET /contract-contingencies` + revisions; `GET`/`PUT /title-escrow` + issues; `GET`/`PUT /buyer-insurance` + quotes/bind/requirements; `GET`/`PUT /final-walkthrough` + observations/issues/complete; `GET /closing-disclosure` + revisions + funds-readiness; `GET`/`PUT /closing-day` + confirm-professional-close; `PATCH /lifecycle`, `POST /pause`, `/resume`, `/cancel`, `/handoff`; `PATCH /documents/:documentId/verification`; `POST /findings/:findingId/disposition`. Controller `apps/backend/src/controllers/homeBuyerTask.controller.ts` (1,166 lines), service `apps/backend/src/services/HomeBuyerTask.service.ts`.
- **Data:** `HomeBuyerChecklist`, `HomeBuyerTask`, plus joins into `InspectionReport`, `InspectionFinding`, `Document`, `Booking`, `ServiceCategoryConfig`, `HouseholdMember`, `Property`.
- **Notes:** There is a **separate acceptance-only surface** at `app/acceptance/home-buyer-lifecycle/` (and its `slice8` sub-route) — both pages call `notFound()` unless `process.env.HOME_BUYER_LIFECYCLE_ACCEPTANCE_FIXTURE === '1'`, so they are genuinely test-only fixtures, not reachable in normal use. The real, production, nav-reachable surface is `/dashboard/properties/[id]/buyer-plan`. Loan-estimate document extraction is OCR/rate-limited (`ocrRateLimiter`, `uploadRateLimiter`) and file-type restricted to PDF/JPEG/PNG/WEBP, 10MB max, 3 files. A frontend audit found Buyer Plan is not registered in the capability/tool-discovery registry (`productFramework/capabilities/definitions/*.ts`) — it's largely compensated for by `dashboard/page.tsx` swapping the entire Home tab to a dedicated `BuyerClosingHome` component for buyer-context properties, so it isn't literally orphaned, but it won't appear in capability search/suggestions on a non-buyer-context property. See [Introduction](../00-introduction.md#known-implementation-alignment-issues).

### Mortgage Refinance Radar
- **What it does:** Monitors current mortgage rates against a property's existing loan and surfaces refinance opportunities, lets the homeowner run "what-if" refinance scenarios, compare Loan Estimates (including OCR extraction from uploaded PDFs/images), track a refinance decision, and set alert preferences (push notifications) for future rate drops.
- **User flow:**
  1. Homeowner opens `/dashboard/properties/[id]/tools/mortgage-refinance-radar` (linked from `RefinanceRadarDashboardCard` on the dashboard and the mobile tool catalog).
  2. Sees current radar status (opportunity or not, based on `PropertyFinancingProfile`); can trigger a fresh evaluation.
  3. Can view rate history/trend, past opportunity history, and a "missed opportunity" insight.
  4. Runs a refinance scenario calculator (with markdown export), uploads Loan Estimates for OCR extraction and comparison, and saves comparisons.
  5. Records a refinance decision (pursue/decline/etc.) and can configure alert preferences + push subscriptions for future rate-drop notifications.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/mortgage-refinance-radar/MortgageRefinanceRadarClient.tsx`, `LoanEstimateComparisonCard.tsx`, `MortgageRateHistoryChart.tsx`, `mortgageRateChartModel.ts`, `refinanceTrustContent.ts`, `mortgageRefinanceRadarApi.ts`.
- **Backend:** `apps/backend/src/refinanceRadar/refinanceRadar.routes.ts`, mounted at `/api`. Key endpoints: `GET/POST /api/properties/:propertyId/refinance-radar` (+`/evaluate`), `GET/POST/DELETE .../refinance-radar/decision(/:decisionId)`, `GET/PUT .../refinance-radar/alert-preferences`, `POST/DELETE .../refinance-radar/push-subscriptions`, `GET .../refinance-radar/history`, `GET .../refinance-radar/missed-opportunity`, `GET .../refinance-radar/rates`, `POST .../refinance-scenario` (+`/export-markdown`, `/saved`), `POST .../refinance-radar/loan-estimates/compare` (+`/export-markdown`, `/handoff-markdown`, `/extract`, `/saved` GET/POST/DELETE), `POST .../refinance-radar/feedback`, `POST .../refinance-radar/telemetry`, and an admin-only `POST /api/admin/refinance-radar/rate-snapshots` (rate ingestion, `requireRole('ADMIN')`). Controller `apps/backend/src/refinanceRadar/refinanceRadar.controller.ts`; supporting services: `refinanceRadar.service.ts`, `refinanceDecision.service.ts`, `refinanceAlertPreference.service.ts`, `refinanceRateMonitor.service.ts`, `refinanceLoanEstimateExtraction.service.ts`, `refinanceLoanEstimateSnapshot.service.ts`, and several comparison/mapper/markdown helpers.
- **Data:** `PropertyFinancingProfile`, `PropertyRefinanceRadarState`, `RefinanceOpportunity`, `RefinanceScenarioSnapshot`, `RefinanceDecision`, `RefinanceLoanEstimateComparisonSnapshot`, `RefinanceRateMonitor`, `NotificationPreference`, `PushSubscription`, plus `DomainEvent` for history.
- **Notes:** There is again a **separate acceptance-only tree** at `app/acceptance/mortgage-refinance-radar/[id]/page.tsx` and `app/acceptance/mortgage-refinance-radar/home-actions/page.tsx`; the latter is explicitly gated (`notFound()` unless `MORTGAGE_REFINANCE_ACCEPTANCE_FIXTURE === '1'`). The real production route is `/dashboard/properties/[id]/tools/mortgage-refinance-radar`, wired into `RefinanceRadarDashboardCard`, sidebar/mobile catalogs. Loan Estimate extraction shares the same OCR/upload rate-limiting pattern as the buyer-plan feature.

### Moving Concierge
- **What it does:** Generates an AI-assisted (Gemini) personalized moving plan around a purchase's closing date — a week-by-week timeline, utility-setup guide, cost estimates, packing schedule, change-of-address checklist, and AI recommendations — tailored to home size, family size, pets, valuables, and move distance.
- **User flow:**
  1. From `/dashboard/moving-concierge` (property picker via `useDashboardPropertySelection`, also reachable with a `propertyId` query param), buyer fills in closing date, addresses, home size/rooms, family size, pets/valuables flags, move distance, and special requirements.
  2. Submits to generate a plan; the AI produces a compressed timeline if the closing date is imminent (<28 days) versus a standard timeline otherwise.
  3. Plan is displayed with editable/completable tasks, utility setup steps, cost breakdown, and packing schedule; the user can save the plan for later, and delete it.
  4. Plan tasks reconcile against the property's canonical work-item tracking (`reconcileMovingPlanTasks` / `projectCanonicalMovingCompletion`) so moving tasks tie back to real completion state rather than being purely local UI state.
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/moving-concierge/page.tsx`, `apps/frontend/src/components/MovingConcierge.tsx`.
- **Backend:** `apps/backend/src/routes/movingConcierge.routes.ts`, mounted at `/api/moving-concierge`. Endpoints: `POST /generate-plan`, `POST /save-plan`, `GET /get-plan/:propertyId`, `DELETE /delete-plan/:propertyId`. Service `apps/backend/src/services/movingConcierge.service.ts` (uses `@google/genai` `GoogleGenAI` client directly; falls back to `getBasicTimeline`/non-AI generation if no AI client is configured) and `movingConciergeTask.service.ts` for canonical task reconciliation.
- **Data:** `MovingPlan` (stored plan JSON + metadata). Reads planning-context decisions via `getPlanningContextDecisions`/`getPlanningContextEnvelope` for a `MOVING_PLAN` decision key, which can mark the plan `NOT_APPLICABLE` for a given property context.
- **Notes:** Requires `CONTRIBUTOR` household role to generate a plan (`assertAccess(userId, propertyId, 'CONTRIBUTOR')`). The route's error handler special-cases a message string `"only available for home buyers"` to return a friendlier 403 — but nothing in the current service code actually throws that exact string (the real applicability gate throws `"Moving planning does not apply to this property context"` instead), so that branch in `movingConcierge.routes.ts` looks like dead/stale error-handling left over from an earlier gating implementation. Reachable via real dashboard navigation, not acceptance-only.

### Home Digital Will
- **What it does:** Lets a household build a structured, sectioned record of critical home/property information for emergencies or estate handoff — e.g. utility shutoffs, insurance/contact info, service provider lists — organized into sections and ordered entries, with named "trusted contacts" the owner can register per section type (e.g. EMERGENCY), and exportable as an offline/printable emergency packet PDF. **Correction: there is no external sharing mechanism today** — see User flow step 4 and Notes below; this was previously described as something a trusted contact could actually use to view their scoped info, which is not what the code does.
- **User flow:**
  1. Household member (`CONTRIBUTOR`+) opens `/dashboard/properties/[id]/tools/home-digital-will` (linked from `PropertyRecordOverview`'s Documents area and the mobile tool catalog).
  2. Creates the will if one doesn't exist yet (`getOrCreateDigitalWill`), then adds sections and drag-reorders them.
  3. Adds entries within each section (reorderable), fills in structured content, and can publish the will (locking/marking it as the current authoritative version).
  4. Adds trusted contacts and can preview a contact-scoped view (`GET /home-digital-wills/:id/trusted-contacts/:contactId/view?sectionType=EMERGENCY`) restricted to specific section types — **but this is a preview for the owner, not a link the contact can use**. See Notes.
  5. Can download a generated "emergency packet" PDF for offline use (`GET .../home-digital-will/emergency-packet.pdf`).
- **Frontend:** `apps/frontend/src/app/(dashboard)/dashboard/properties/[id]/tools/home-digital-will/HomeDigitalWillClient.tsx`, `homeDigitalWillApi.ts`, `homeDigitalWillActivation.ts`, `types.ts`.
- **Backend:** `apps/backend/src/routes/homeDigitalWill.routes.ts`, mounted at `/api`. Property-scoped: `GET/POST /api/properties/:propertyId/home-digital-will` (both require `CONTRIBUTOR`), `GET .../home-digital-will/emergency-packet.pdf`. Will-scoped (by will id, not property id): `PATCH /api/home-digital-wills/:id`, `POST /api/home-digital-wills/:id/publish`, `GET /api/home-digital-wills/:id/sections` (+`/reorder`), `GET /api/home-digital-wills/:id/trusted-contacts/:contactId/view`, `GET/POST /api/home-digital-wills/:id/trusted-contacts`. Section/entry-scoped: `PATCH/DELETE /api/home-digital-will-sections/:sectionId`, `GET/POST /api/home-digital-will-sections/:sectionId/entries` (+`/reorder`), `PATCH/DELETE /api/home-digital-will-entries/:entryId`, `PATCH/DELETE /api/home-digital-will-trusted-contacts/:contactId`. Controller `apps/backend/src/controllers/homeDigitalWill.controller.ts`, service `apps/backend/src/services/homeDigitalWill.service.ts`; PDF generation in `apps/backend/src/services/emergencyPacket.service.ts`.
- **Data:** `HomeDigitalWill`, `HomeDigitalWillSection`, `HomeDigitalWillEntry`, `HomeDigitalWillTrustedContact`.
- **Notes:** Property-scoped routes require `CONTRIBUTOR` role via `requireHouseholdRole('CONTRIBUTOR')`. **Correction, now verified rather than assumed:** the entire `homeDigitalWill.routes.ts` router is behind `router.use(authenticate)` (line 46), and `getTrustedContactScopedView()` (`homeDigitalWill.service.ts` ~line 397) additionally calls `assertWillOwnership(willId, userId, 'OWNER')` — the *requesting* user must themselves be the property's OWNER. This means the "trusted-contact view" is a preview the owner uses while logged in as themselves to see what a given contact's scoped view would look like; it is **not** a mechanism for actually sharing anything with an external trusted contact — a real contact (who by definition doesn't have OWNER access to the property, and may have no C2C account at all) cannot use this endpoint. The IDs in the URL are not a security boundary standing in for a share link; the ownership check is. If external sharing is the intended feature, it isn't built yet. The emergency-packet PDF endpoint is explicitly documented in-code as "not a token-based external share" either — it's for the household's own authenticated offline use. Reachable via real navigation, not acceptance-only.
