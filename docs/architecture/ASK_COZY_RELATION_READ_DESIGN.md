# Relation-read design for DATA_POINT_READ (design only; nothing built)

**Status (updated 2026-11-12): slice 1 BUILT (buyer checklist -> tasks, catalogue v5); everything else still design only.** Original status: DESIGN for owner review.  Needed by claims, sale readiness items (`SaleReadinessItem` by `saleCaseId`), buyer tasks and milestones (by `checklistId`), record versions/links (by `recordId`) and any child without a plain `propertyId`. One mechanism, so there are no one-off readers.

## Contract
1. **Allowlisted relation paths only.** A path is declared in code: `{ child, parent, parentKey, depth: 1 }`, e.g. `HomeBuyerTask -> HomeBuyerChecklist (checklistId)`. No path, relation or field name comes from the message or from a model; the plan carries a path id, never a name. Depth is 1 (parent to child); deeper chains need a new reviewed path.
2. **Property scoping at the authoritative parent.** The query is parent-first: the parent is found by `propertyId` (the parent has a plain column or is a singleton), then children by `parentKey IN (parent ids)`. A child id from a prior turn is never trusted: replay re-resolves through the parent.
3. **Visibility inherited.** If the parent has a visibility rule (Home Records: `visibleRecordWhere(role)`), it is applied to the parent first; an invisible parent means its children read as not found, never "exists but hidden".
4. **Lifecycle filters on both sides.** Parent (active, not trashed/cancelled/closed as appropriate) and child (not deleted, not superseded, status per entity) are declared per path, not defaulted.
5. **Per-field floors** are the existing catalogue floors; the path adds none, and a child may not be read at a lower floor than its parent's strictest field.
6. **Row limits.** Parents at most 5, children at most 50 per read, hard `take`; over the limit asks which, never lists all.
7. **Ambiguity.** More than one matching child or parent and none named: one clarification listing at most 8 display names (existing AMBIGUOUS behaviour). A name matches on the child's declared label only.
8. **Provenance.** Each row carries its own `sourceType`/`sourceId` for the child, plus the parent id; confidence/source limitations follow the existing per-record rule.
9. **Replay and refresh.** Authorization re-checks the child through the parent with the same predicates (new `CHECKS` entries whose `where` includes the parent relation filter, e.g. `{ id, parent: { propertyId } }`), at the current role.
10. **Moves, deletes, privacy changes, supersession.** A child that moves parent, is deleted, becomes private or is superseded fails the replay check and the section is redacted (existing `REDACT_SECTION`); the answer is not recomposed from a stale value.
11. **No model-supplied names.** The request plan's `dataPointId` resolves against the catalogue; relation paths are keyed by catalogue entity.

First slices carry **structured fields only**: status, due/target date, completed date, priority or sequence, structured category/type. Deferred until separately approved: free-form descriptions, notes, attachments, assignee contact details, external identifiers. Claims: status and major lifecycle dates CONTRIBUTOR; amount, payout, settlement, applied deductible, reserve, payment details, full claim number and account identifiers OWNER; claim amounts are not CONTRIBUTOR by default.
**Exact ids still need approval before any build** (the catalogue approves exact ids, not field classes). ## Slice 1 as built (catalogue v5, owner-approved ids 2026-11-12)
`RELATION_ENTITIES` allowlists `HomeBuyerTask -> HomeBuyerChecklist (checklistId)`; the reader mode `RELATION_CHILD` finds the property-scoped parent (`take: 5`), then children ONLY via `checklistId IN parents` with `applicability != NOT_APPLICABLE` (`take: 50`, ordered by priority then due date). Ids (all VIEWER): `buyerTask.status`, `buyerTask.dueDate` (`dueAt`), `buyerTask.completedDate` (`completedAt`), `buyerTask.priority`. The task title only selects a row (most specific title wins; equal specificity is ambiguous) and is never returned as a value; ambiguity answers with a count and no titles. Routing: compound cues (`buyer task`, `buying task`, `closing task`) outrank the generic `task`; bare `task` stays maintenance; a message mixing buyer words with `maintenance` resolves to nothing, deterministically. Replay re-resolves the task through its CURRENT property-scoped checklist (`checklist: { propertyId }`, applicable). **Not built:** milestones, sale-case children, record versions, claims. **Lifecycle (owner rules 2026-11-12, built after external review found stale-value risk):** the parent query selects the checklist status and the child query always selects the child status and parent key. ACTIVE reads normally; PAUSED answers with "This buyer journey is paused."; CANCELLED, HANDED_OFF and ARCHIVED journeys are historical reads: a lone unnamed row is not defaulted (the row must be named) and the value carries "may no longer represent an active obligation". A CANCELLED or NOT_NEEDED task answers `buyerTask.status` plainly, but its date or priority is worded as a recorded past value ("Your buyer task is cancelled. Its recorded date was ..."), never "is due"; for milestones the inactive statuses are CANCELLED and WAIVED (MISSED keeps its date because its status says so). NOT_APPLICABLE tasks stay excluded. The limitation is part of the result, so replay of the stored answer keeps it. Assignment to an external contact is workflow, not an authorization boundary; the points expose neither assignee nor contact. Executed: `dataPointRead.test.js` 37/37; not run against a real database.

## Slice 2 as built (catalogue v6): buyer journey -> milestones
Same `HomeBuyerChecklist` parent, same reader mode, same lifecycle rules. Exact ids (owner-approved, VIEWER): `buyerMilestone.status`, `buyerMilestone.dueDate` (`dueAt`), `buyerMilestone.completedDate` (`completedAt`), `buyerMilestone.type`. The STRUCTURED `type` enum selects a row (words of the enum value, most specific wins, so `inspection contingency` does not also match `inspection`) and is returned as a value; `customLabel`, `notes`, `responsibleUserId`, `sourceEntityId`, `sourceDocumentId` are never selected. Compound cues: buyer / buying / closing / purchase + milestone. Replay: `{ id, checklist: { propertyId } }`. A `CUSTOM` milestone has no structured name, so it can only be read as the lone default or after the user disambiguates another way (not yet supported).
**Does the mechanism generalize?** Slice 2 needed only a new `ENTITY_SPECS` entry, a `RELATION_ENTITIES` row, catalogue points and a source check; no new reader branch. That is one data point (same parent), not proof for other parents.
**Sale-case children (next, not built):** `SaleReadinessItem` has `saleCaseId` and `PropertySaleCase` has `propertyId @unique`, so the parent-scoping model is the same (schema read only). Differences to settle before building: items carry cost and value-add ranges (owner-only amounts), free-form `detail`, and a `sourceEntityType/sourceEntityId` pair; the structured fields would be `status`, `category`, `requirementClass`, `dueAt`, `resolvedAt`. Then record versions, then claims.

## Slice 3 as built (catalogue v7, 2026-11-13): sale case -> sale-readiness items
`RELATION_ENTITIES.SaleReadinessItem` = parent `PropertySaleCase` (`propertyId @unique`), key `saleCaseId`, one level. Each path now carries `parentNoun`, `normalStatuses` and `pausedStatuses`, so lifecycle wording is not buyer-specific. Owner-approved ids (VIEWER): `saleItem.status`, `saleItem.category`, `saleItem.requirementClass`, `saleItem.dueDate` (maps to `dueAt`). Not catalogued: title (selects only), detail, cost and value-add ranges, waiver reason, source entity id, user ids, canonical work-item id. Lifecycle: PREPARING, LISTED, UNDER_CONTRACT normal; CLOSED and CANCELLED need a named item and add a historical limitation; RESOLVED and WAIVED answer status plainly and a due date as a past value; OPEN and PURSUING normal. Replay re-checks `{ id, saleCase: { propertyId } }`. Remaining order: record versions, then claims.

## Slice 4 as built (catalogue v8, 2026-11-13): record -> versions
Unlike slices 1-3 this is not parent-first: a property has many records, so the parent must be NAMED and pass `visibleRecordWhere(role)` + ACTIVE + not trashed before any version is read (reader mode `RECORD_VERSION`; the path is also listed in `RELATION_ENTITIES` so the model/scoping checks cover it). Ids (VIEWER): `recordVersion.number`, `.uploadedDate`, `.scanStatus`, `.integrityStatus`. Only the named record's current version (or `version N`) is returned. Remaining: claims.

## Claims (catalogue v9, 2026-11-13): not a relation read
Schema check: `Claim` carries `propertyId` directly, so it is read as a NAMED entity through the existing mode (property-scoped, title selects, display by type) rather than through the insurance-policy parent proposed in the original order. The relation-read design therefore has four built paths (tasks, milestones, sale items, record versions) and claims needed none; claim checklist items, documents and timeline events (true children) remain unbuilt.
