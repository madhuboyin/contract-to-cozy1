## T01 — Several domains have active attention items

**Required:** "Deterministic categorized ordering with source/time/uncertainty."

**Verdict: PASS.**

`HOME_ACTIONS` is the strongest evidence here. `rankAndDeduplicateHomeActions` (`homeActions.service.ts:726–784`) sorts by `HOME_ACTION_PRIORITY_ORDER[priority]`, then `score.score`, then `a.winner.id.localeCompare(b.winner.id)` as an explicit final tie-break — fully deterministic, no model involvement in ordering, and the `GROUPED_LIST` block's own description says so directly: "Priority and order come from the canonical Home Action feed. Ask does not independently rerank them" (`askOrchestrator.service.ts:4502`). Each item's `meta` array carries `action.source.kind` (source), `action.timing.dueAt`/`rationale` (time), and `action.confidence.label` (uncertainty) — all three required fields present per item. `INSPECTION_FINDINGS`' query independently confirms the same discipline at the database level: `orderBy: [{ severity: 'asc' }, { updatedAt: 'desc' }]` (`askOrchestrator.service.ts:3055`) — a DB-enforced deterministic order with its own tie-break, not application-level sorting that could drift.

## T02 — Same underlying issue appears from two producers

**Required:** "Honest grouping/deduplication with all material evidence retained."

**Original verdict: PARTIAL.**

The dedup mechanism itself is genuinely careful, not a naive first-wins collapse. `rankAndDeduplicateHomeActions` merges by `canonicalKey`, and when two producers project the same concern off different clocks, timing is explicitly merged to the more material value rather than arbitrarily kept from the "winner": `current.timing = isWeatherPreparationRevision ? laterWeatherPreparationTiming(...) : earlierTiming(current.timing, action.timing)`, with a code comment explaining why ("the homeowner should see the earliest actionable date, not the winner's"). Every merged-away duplicate's id is retained in `deduplication.mergedActionIds` for traceability.

What wasn't retained: the merged-away duplicate's own `evidence` array. The winning action kept only its own `evidence` list (`{ ...winner, timing: entry.timing, ... }` — no evidence union), and `homeActionsResult`'s `EVIDENCE` block iterates only `selectedActions` (the winners) for evidence items (`askOrchestrator.service.ts:4527–4534`). If two producers surfaced the same concern with materially different supporting evidence (e.g., one has a specific dollar estimate the other lacks), only the winning producer's evidence survived into what the homeowner saw — the losing producer's evidence was dropped, not merged, with only its bare ID left as a trace.

**FIXED, same session, 2026-09-17.** `rankAndDeduplicateHomeActions` (`homeActions.service.ts`) now tracks a `mergeEvidence` union alongside the existing timing merge: every action sharing a `canonicalKey` contributes its own `evidence` array into the group's accumulated set, deduplicated by `EvidenceRef.id` (confirmed unique per evidence item via `EvidenceRefSchema`), regardless of which action ends up as the winner on score/priority. The final returned entry now explicitly sets `evidence: entry.evidence` (the merged set), the same override pattern the existing `timing: entry.timing` line already used — so `homeActionsResult`'s downstream `EVIDENCE` block, which already iterates each selected action's own `evidence` array unmodified, now surfaces the merged set with no changes needed on that side. This brings evidence retention to the same bar timing already had: material information from a losing duplicate is unioned in, not discarded, satisfying "all material evidence retained" for the property this scenario's own literal wording asks about.

**Verification level: 3 new unit tests** in `tests/unit/phase2HomeActions.test.js` (a two-producer merge with distinct evidence retains both; identical evidence ids across two producers are deduplicated, not doubled; a three-way merge unions evidence from all three producers, not just the top two) — all pass, alongside a clean `tsc --noEmit` and the file's pre-existing 35-test suite (one unrelated, pre-existing frontend-component-content test failure confirmed present before this change too, via `git stash`; not touched or caused by this fix). **Not** database- or browser-verified.

## T03 — Switch from selected-property to all-property view

**Required:** "Property labels and boundaries preserved; no cross-property action retargeting."

**Original verdict: FAIL.** (Now `PASS` after 2 rounds of fixes — see below: round 1 built the all-property view, round 2 closed the per-item labeling gap external review found in round 1's own fix.)

There was no all-property view to switch to. `askOperationRegistry.ts`'s own `ASK_OPERATION_DEFINITIONS` showed `HOME_ACTIONS`, `MAINTENANCE_FORECAST`, `INTELLIGENCE_ENVELOPE_QUERY`, `HOME_CHANGE_SUMMARY`, and `INSPECTION_FINDINGS` all declared `requiresProperty: true` (confirmed by direct grep: `HOME_ACTIONS: definition('HOME_ACTIONS', ..., true, ...)`, same for the other four). Across the entire 77-operation registry, only 5 operations pass `false` — `CAPABILITY_DISCOVERY`, `EMERGENCY_BOUNDARY`, `UNSAFE_RESTRICTED_BOUNDARY`, `OUT_OF_SCOPE_BOUNDARY`, `GROUNDED_GUIDANCE` — none of which are attention/list operations. A repository-wide search for `allProperty`/`ALL_PROPERT`/`portfolio` inside `apps/backend/src/services/ask/` returned zero matches. This wasn't a case of an existing mechanism having a gap (like T02); the capability the scenario names didn't exist at all.

This differed from Protection's P08 (`DISMISS`), which the FRD explicitly defers to a named later phase and which was therefore left unscored rather than failed. ATT-104 ("Selected-property and all-property modes are distinct...") carries no such phase deferral, and Phase 5's own bullet lists "property boundary" as in-scope work for this phase. Originally scored FAIL rather than left untestable, because the FRD's own phase sequencing says this requirement should already be met.

**FIXED, same session, 2026-09-17, scoped to `HOME_ACTIONS`; re-scored `PASS` → `PARTIAL` 2026-09-17, external review.** Rather than changing `HOME_ACTIONS`'s `requiresProperty: true` registry contract — which would ripple through routing and execution creation, both of which currently assume a Home Actions turn always has exactly one property — the fix adds an explicit, additive all-property *mode* inside the handler itself. A new `isAllPropertyAttentionRequest` gate recognizes a bounded set of explicit framings ("all my properties," "across all my homes," "every property"); when it matches and the homeowner has access to more than one property, `allPropertyHomeActionsResult` aggregates each accessible property's own governed `getHomeActionFeed` call (the SAME canonical pipeline the single-property view already uses — not a shortcut or a lighter recomputation) into a `GROUPED_LIST` sectioned strictly by property.

This satisfies ATT-104's second half — *"cannot merge records across properties"* — cleanly: each property's feed keeps its own already-deduplicated item list in its own section; there is no second cross-property dedup/rerank pass, so nothing from two different properties is ever combined into one entry. "No cross-property action retargeting" holds by construction, not by a separate guard: every item's `href` comes directly from `action.primaryCta.href`, which the single-property view already uses unmodified and which is built entirely within that property's own `getHomeActionFeed(property.id, userId)` call — there is no shared "current property" substitution anywhere in the aggregation path that could misdirect an action from one property onto another. The accessible-property list itself reuses the same owned-plus-household-member access boundary `property.service.ts`'s own `getUserProperties` already establishes (without its heavy appliance/health-score hydration, which this attention view has no use for) — the query *is* the access check, so no separate per-property recheck is needed. A property whose feed computation fails is disclosed as unavailable rather than silently dropped or substituted (consistent with T08's XRES-004 discipline elsewhere in this document), and the property list is capped at 10 with an explicit "showing the first N of M" disclosure if a homeowner has more than that.

**Correction (external review): ATT-104's first half — *"labels property on every item"* — is NOT met, confirmed by direct re-read of the item-construction code (`askOrchestrator.service.ts:4487–4501`).** Property identity is attached only at the `GROUPED_LIST` section's own `title`/`id` (`property-${property.id}`); each individual item's own fields are `{ id, title, description, meta, status, href }`, and `meta` carries only `[priority, timing, confidence]` — no property id, label, or any other per-item property attribution at all. Confirmed against the shared `GroupedListItemSchema` (`ask.contract.ts:101–112`): it has no property field for an item to carry even if the handler wanted to set one. The FRD's own literal text says "on every item," not "grouped under a correctly labeled section" — a real, textually precise distinction, since anything that reads or displays an item independent of its section context (a flattened list, a screen reader jumping directly to a result, any future feature that pulls individual items out of their `GROUPED_LIST` wrapper) has no way to recover which property that item belongs to. Downstream mutation safety is unaffected (every item's `href` is still correctly scoped, per the paragraph above), but the specific, literal acceptance requirement is not met as written.

**FIXED (2nd round), same session, 2026-09-17: `PASS`.** `meta`'s existing free-form string array (`z.array(z.string()).max(6)`, already rendered as a plain joined string per item by the frontend's generic renderer — `AskWorkspace.tsx:483`, `item.meta.join(' · ')`, no schema change needed) now carries `property.label` as its own first entry on every item this handler emits, including the unavailable/empty/degraded placeholder items introduced by the T08 fix below — not only the real action items. This directly closes ATT-104's first half: an item read independent of its `GROUPED_LIST` section (flattened, screen-reader-navigated, or pulled out by a future feature) now carries its own property attribution in its own data, not only inherited from a wrapper it may not still be inside. The section-building logic was extracted into a new pure, exported function, `buildAllPropertyHomeActionSection(property, feed)` (`askOrchestrator.service.ts`), so this is directly unit-tested rather than only type-checked.

Scoped deliberately to `HOME_ACTIONS` — the flagship attention aggregator named throughout this document and Phase 0 — not a platform-wide claim that all 5 Phase-5 operations now support all-property mode; they don't. Falls through unchanged to the ordinary single-property read when 0 or 1 property is accessible, so an ordinary single-property homeowner sees no behavior change at all.

**Verification level: 9 new unit tests total across 2 files.** `tests/ask/allPropertyAttentionRequest.test.js` (3 tests) covers the message-detection gate directly (6 recognized phrasings, 3 ordinary single-property questions correctly excluded, a bare "property" mention without "all"/"every" correctly excluded). `tests/ask/allPropertyHomeActionSections.test.js` (6 new tests, added with the round-2 fix) covers the extracted `buildAllPropertyHomeActionSection` pure function directly against fixture feeds: a healthy feed's item carries the property label as its own `meta[0]`, not only the section title; the unavailable/empty placeholder items also carry it; a degraded-producer feed surfaces a `CAUTION` disclosure item alongside real actions (T08, see below) without losing its own property label; two degraded producers are both named. All pass, alongside a clean `tsc --noEmit`, a fresh-parse check, and the full pre-existing 659-test Ask suite (658/659 green, no regression — the 1 failure is the same pre-existing, unrelated frontend-component-content test confirmed present before any change this session via `git stash`).

What remains **untested by anything in this session** — genuinely DB-dependent behavior the extracted pure function doesn't cover:
- **Property isolation** — that two properties' item lists are never merged, deduplicated together, or cross-contaminated in the `GROUPED_LIST` sections, against real multi-property data.
- **Authorization** — that a property the homeowner does *not* have access to (not owned, not a household member) never appears in the aggregated list, and that a revoked household membership is reflected on the next ask.
- **Partial-source behavior against a real failure** — the unit tests exercise the fixture shapes directly; whether `getHomeActionFeed` throwing or returning degraded diagnostics in a live database actually produces those fixture shapes end to end is not exercised.
- **Action targeting** — that clicking an item from Property B's section actually navigates to and would act on Property B, not the anchor property or Property A.

This is a real, narrower-but-still-open verification gap — `accessiblePropertiesForAllPropertyAttention` and the outer `allPropertyHomeActionsResult` orchestration (as opposed to the now-tested `buildAllPropertyHomeActionSection` section-building logic) still compose `getHomeActionFeed`, an already-heavy function with dozens of nested service dependencies (`BuyerAcquisitionService`, `materializeRecommendationsForProperty`, several reconciliation passes) that would require extensive mocking to exercise in isolation without a live database; closing it would need either that mocking investment or a database/browser-backed integration test, neither of which exists this session. **Not** database- or browser-verified.

## T08 — Source becomes unavailable

**Required:** "Item becomes partial/unavailable; no 'all clear' state."

**Verdict: PASS (2nd round fix).** Originally scored PARTIAL after external review found a track-level scoring inconsistency; `HOME_ACTIONS`'s own single-property gap was fixed, briefly bringing this to PASS; a second external review then found the same-session T03 all-property mode bypasses the fix entirely (see below) — re-scored PARTIAL; the all-property path now also propagates `unavailableProducers`, closing the gap a 2nd time.

**Correction (external review):** the original PASS scored the whole track based on one of five operations (`INTELLIGENCE_ENVELOPE_QUERY`), while its own prose in the same paragraph admitted the flagship operation (`HOME_ACTIONS`) lacked the mechanism. Elsewhere in this same audit series, an identical situation — a requirement genuinely met by some operations in a group and genuinely not met by others — was scored PARTIAL (Financial's F05: true for `REFINANCE_ANALYSIS`/`OWNERSHIP_COSTS`/`SAVINGS_OPPORTUNITIES`, false for `CAPITAL_RESERVE_PLAN`). T08 was corrected to PARTIAL to match. `HOME_ACTIONS`'s own gap is fixed below, so the track-level verdict is now PASS again — on a genuinely stronger basis than the original overclaim, since both operations now implement the requirement rather than only one.

`INTELLIGENCE_ENVELOPE_QUERY` implements the requirement genuinely well. `queryIntelligenceEnvelope`'s result carries a `page.diagnostics` array; when non-empty, the operation returns `status: 'READY_WITH_LIMITATIONS'` with `reasonCode: 'INTELLIGENCE_ENVELOPE_PARTIAL'` and an explicit `BOUNDARY` block naming the exact failing producer and code: `body: page.diagnostics.map((diagnostic) => \`${diagnostic.producerModel}: ${diagnostic.code}\`).join('; ')` (`askOrchestrator.service.ts:6645–6653`). `HOME_ACTIONS` — the operation named throughout this document and Phase 0 as the flagship attention aggregator, and arguably the operation T08's scenario text is most centrally about, since it's the one that genuinely aggregates multiple producers into one feed — **originally did not implement this requirement.** Its `diagnostics` object tracked counts (`candidateCount`, `surfacedCount`, `duplicateCount`, `suppressedCount`, `emptyStateReason`) but had no per-producer up/down signal comparable to Envelope's. Two producers inside `getHomeActionFeed` — the environment-insight report and personalization — already caught their own failures and degraded gracefully (returning `null`/a `FAILED` status rather than throwing), but neither failure was tracked anywhere a homeowner-facing response could read it: `personalizationStatus` was computed and stored in `diagnostics.personalization.status`, and `homeActionsResult` never read that field at all, confirmed by a direct grep of every `diagnostics.` reference in the file. A homeowner asking Home Actions while personalization or the environment producer was down got a normal-looking, non-empty response with zero disclosure.

**FIXED, same session, 2026-09-17.** `getHomeActionFeed` now tracks a `diagnostics.unavailableProducers: string[]` list, populated from the two producers it already safely catches and degrades from (`ENVIRONMENT_REPORT`, `PERSONALIZATION`) — deliberately **not** extended to `getOrchestrationSummary`/`getPromotedHomeActions`, which remain unwrapped: an unhandled failure in either still throws and is caught by `homeActionsResult`'s own outer try/catch into an honest, track-wide `UNAVAILABLE`, which already satisfies "no all-clear state" for that specific failure mode without this fix inventing a risky synthetic fallback for either function's large, otherwise-required return shape. `homeActionsResult` now reads this list: when non-empty, it sets `status: 'READY_WITH_LIMITATIONS'` with `reasonCode: 'HOME_ACTION_PRODUCER_UNAVAILABLE'`, sets the summary's own `tone` to `CAUTION`, and pushes an explicit `BOUNDARY` block naming which producer(s) were unavailable — the same shape as Envelope's own diagnostics disclosure, via a small extracted, unit-tested formatter (`formatUnavailableHomeActionProducers`). Pushed unconditionally on diagnostics presence, not gated on whether the feed is otherwise empty, mirroring Envelope's own placement.

**Verification level (round 1): 4 new unit tests** in `tests/ask/homeActionProducerAvailability.test.js` covering `formatUnavailableHomeActionProducers` directly (single known producer labeled by homeowner-facing name; two producers joined readably; an unrecognized producer code falls back to a lowercased label rather than throwing; an empty list produces an empty string) — all pass, alongside a clean `tsc --noEmit`, a direct fresh-parse check on both edited files, and the full pre-existing 107-test combined Ask/homeActions suite (106/107 green; the one failure is an unrelated, pre-existing frontend-component-content test confirmed present before this change via `git stash` during the T02 fix earlier this session). **Verification level (round 2): 3 more of the 6 new tests in `tests/ask/allPropertyHomeActionSections.test.js`** (shared with the T03 round-2 fix, same file) specifically exercise the all-property degradation path: a degraded-producer feed with real actions surfaces the `CAUTION` item alongside them without dropping any; a degraded-producer feed with zero actions still discloses the degradation rather than only showing the empty state; two degraded producers are both named in the disclosure text. The producer-failure *detection* itself (does `getEnvironmentReportForProperty`/`materializeRecommendationsForProperty` actually failing end to end produce the disclosure) is **not** independently exercised in either round — `getHomeActionFeed` is an already-heavy, DB-dependent function that would need extensive mocking to test in isolation without a live database, the same STATIC-verification boundary applied throughout this audit series. **Not** database- or browser-verified.

Scored PASS for the single-property path: the requirement is genuinely met for the two producers this feed can safely degrade from without risking a broken fallback, and the remaining gap (orchestration/promoted-actions failures) is honestly covered by the existing whole-feed `UNAVAILABLE` path rather than a silent, undisclosed partial state — satisfying T08's literal "no all-clear state" bar even where per-producer granularity isn't attempted.

**Correction (external review): re-scored `PASS` → `PARTIAL` 2026-09-17 — the all-property mode added for T03 in this same session bypasses this fix entirely.** `homeActionsResult`'s dispatch (`askOrchestrator.service.ts:4564`) routes to `allPropertyHomeActionsResult` and returns *before* the single-property code path (including the `unavailableProducers` disclosure this fix built) ever runs. The all-property path's own unavailability handling only covers the case where `getHomeActionFeed` *throws entirely* (line 4467's try/catch, rendered as an "unavailable" section) — a property whose feed call *succeeds* but has environment-report or personalization silently degraded inside it renders as a normal, fully-populated section with no `CAUTION` tone and no `BOUNDARY` disclosure. This is a genuine reintroduction of the exact defect this fix closed, in a code path that didn't exist when the fix was written earlier in the same session — not a new claim about code this fix was ever meant to cover, but a real gap in what "T08 passes" now means given T03 shipped alongside it. ## T09 — Complete underlying work from another surface

**Required:** "Attention item reconciles without duplicate action."

**Verdict: PASS.**

All 5 Phase-5 operations recompute fully live from canonical Prisma state on every call — none of them cache a prior result. `getHomeActionFeed` is called fresh inside `homeActionsResult` with no memoization; `listForecast`/`generateForecast` read/write the live forecast table; `queryIntelligenceEnvelope` reads the live envelope; `listPropertyChanges` and the `prisma.inspectionFinding.findMany` call in `inspectionFindingsResult` are both direct, unmemoized queries. Because a Home Action is *derived* from live canonical state rather than stored as an independent redundant record, completing the underlying work on another surface (e.g., marking a maintenance task done directly) means the next ask simply no longer generates that candidate — there is no separate "attention item" record that could go stale or need a second, duplicate action to clear. This is architectural rather than a specific reconciliation feature, consistent with ATT-110's requirement and with the same live-recompute pattern already confirmed across every other track in this audit series.

## T10 — No actionable items remain

**Required:** "Honest completion/empty state with no forced suggestion."

**Verdict: PASS.**

Every operation in this track has a distinct, honest empty state rather than a generic "nothing to see" or a forced next action: `HOME_ACTIONS` uses `homeActionEmptyCopy(feed.diagnostics.emptyStateReason)`, varying the message by the actual reason (not a single canned string); `HOME_CHANGE_SUMMARY`'s empty state states explicitly, "This covers [sources]. It is not a confirmation that nothing at all happened at this property — only that no material change was recorded in these sources" (`askOrchestrator.service.ts:3416–3417`) — actively guarding against the false-completeness reading; `INSPECTION_FINDINGS` returns "No open confirmed inspection findings" with an optional (not forced) link to the Inspection Hub and an empty `suggestions` array; `MAINTENANCE_FORECAST`'s `NOT_APPLICABLE` branch names the specific reason ("no verified HVAC, roof, or water-heater inventory items"). None of these branches carry a mandatory action — every action offered is a `style: 'PRIMARY'`/`'SECONDARY'` link the homeowner can ignore, not a control the operation requires interacting with to proceed.
