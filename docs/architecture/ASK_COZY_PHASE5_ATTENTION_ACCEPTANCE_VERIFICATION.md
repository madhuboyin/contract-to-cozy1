## Why only 6 of the 10 scenarios

T04–T07 (`DISMISS`, `ALREADY_HANDLED`, `REMIND_LATER`, and dismiss-near-safety) are explicitly out of scope for Phase 5 — the FRD's own Phase 5 bullet says "Do not expose `DISMISS`, `ALREADY_HANDLED` or `REMIND_LATER` in this phase," and Phase 5's exit criterion only names T01–T03 and T08–T10. That gate is Phase 9's ("T04–T07 pass and every exposed control has a tested typed dispatch outcome"), already confirmed absent platform-wide during Phase 0 Stage 1 (`interactionDispatch.ts` maps `DISMISS`/`REMIND_LATER` to `UNSUPPORTED`) and reconfirmed untestable for the same reason in the Phase 8 Protection document (P08). Scoring them here would just repeat that finding under a different scenario ID.

## Methodology

Same as the Phase 6/7/8/Financial verifications: PASS (fully confirmed by code), PARTIAL (part of the requirement met, a specific part isn't), FAIL (confirmed not met — reserved for a requirement the FRD says is in scope *now*, as distinct from Protection's P08, which is unscored because its own precondition is explicitly deferred to a later phase).

## T01 — Several domains have active attention items

**Required:** "Deterministic categorized ordering with source/time/uncertainty."

**Verdict: PASS.**

`HOME_ACTIONS` is the strongest evidence here. `rankAndDeduplicateHomeActions` (`homeActions.service.ts:726–784`) sorts by `HOME_ACTION_PRIORITY_ORDER[priority]`, then `score.score`, then `a.winner.id.localeCompare(b.winner.id)` as an explicit final tie-break — fully deterministic, no model involvement in ordering, and the `GROUPED_LIST` block's own description says so directly: "Priority and order come from the canonical Home Action feed. Ask does not independently rerank them" (`askOrchestrator.service.ts:4502`). Each item's `meta` array carries `action.source.kind` (source), `action.timing.dueAt`/`rationale` (time), and `action.confidence.label` (uncertainty) — all three required fields present per item. `INSPECTION_FINDINGS`' query independently confirms the same discipline at the database level: `orderBy: [{ severity: 'asc' }, { updatedAt: 'desc' }]` (`askOrchestrator.service.ts:3055`) — a DB-enforced deterministic order with its own tie-break, not application-level sorting that could drift.

## T02 — Same underlying issue appears from two producers

**Required:** "Honest grouping/deduplication with all material evidence retained."

**Original verdict: PARTIAL.**

The dedup mechanism itself is genuinely careful, not a naive first-wins collapse. `rankAndDeduplicateHomeActions` merges by `canonicalKey`, and when two producers project the same concern off different clocks, timing is explicitly merged to the more material value rather than arbitrarily kept from the "winner": `current.timing = isWeatherPreparationRevision ? laterWeatherPreparationTiming(...) : earlierTiming(current.timing, action.timing)`, with a code comment explaining why ("the homeowner should see the earliest actionable date, not the winner's"). Every merged-away duplicate's id is retained in `deduplication.mergedActionIds` for traceability.

What wasn't retained: the merged-away duplicate's own `evidence` array. The winning action kept only its own `evidence` list (`{ ...winner, timing: entry.timing, ... }` — no evidence union), and `homeActionsResult`'s `EVIDENCE` block iterates only `selectedActions` (the winners) for evidence items (`askOrchestrator.service.ts:4527–4534`). If two producers surfaced the same concern with materially different supporting evidence (e.g., one has a specific dollar estimate the other lacks), only the winning producer's evidence survived into what the homeowner saw — the losing producer's evidence was dropped, not merged, with only its bare ID left as a trace.

**FIXED, same session, 2026-09-17.** `rankAndDeduplicateHomeActions` (`homeActions.service.ts`) now tracks a `mergeEvidence` union alongside the existing timing merge: every action sharing a `canonicalKey` contributes its own `evidence` array into the group's accumulated set, deduplicated by `EvidenceRef.id` (confirmed unique per evidence item via `EvidenceRefSchema`), regardless of which action ends up as the winner on score/priority. The final returned entry now explicitly sets `evidence: entry.evidence` (the merged set), the same override pattern the existing `timing: entry.timing` line already used — so `homeActionsResult`'s downstream `EVIDENCE` block, which already iterates each selected action's own `evidence` array unmodified, now surfaces the merged set with no changes needed on that side. This brings evidence retention to the same bar timing already had: material information from a losing duplicate is unioned in, not discarded, satisfying "all material evidence retained" for the property this scenario's own literal wording asks about.

**Verification level: 3 new unit tests** in `tests/unit/phase2HomeActions.test.js` (a two-producer merge with distinct evidence retains both; identical evidence ids across two producers are deduplicated, not doubled; a three-way merge unions evidence from all three producers, not just the top two) — all pass, alongside a clean `tsc --noEmit` and the file's pre-existing 35-test suite (one unrelated, pre-existing frontend-component-content test failure confirmed present before this change too, via `git stash`; not touched or caused by this fix). **Not** database- or browser-verified.

## T03 — Switch from selected-property to all-property view

**Required:** "Property labels and boundaries preserved; no cross-property action retargeting."

**Original verdict: FAIL.**

There was no all-property view to switch to. `askOperationRegistry.ts`'s own `ASK_OPERATION_DEFINITIONS` showed `HOME_ACTIONS`, `MAINTENANCE_FORECAST`, `INTELLIGENCE_ENVELOPE_QUERY`, `HOME_CHANGE_SUMMARY`, and `INSPECTION_FINDINGS` all declared `requiresProperty: true` (confirmed by direct grep: `HOME_ACTIONS: definition('HOME_ACTIONS', ..., true, ...)`, same for the other four). Across the entire 77-operation registry, only 5 operations pass `false` — `CAPABILITY_DISCOVERY`, `EMERGENCY_BOUNDARY`, `UNSAFE_RESTRICTED_BOUNDARY`, `OUT_OF_SCOPE_BOUNDARY`, `GROUNDED_GUIDANCE` — none of which are attention/list operations. A repository-wide search for `allProperty`/`ALL_PROPERT`/`portfolio` inside `apps/backend/src/services/ask/` returned zero matches. This wasn't a case of an existing mechanism having a gap (like T02); the capability the scenario names didn't exist at all.

This differed from Protection's P08 (`DISMISS`), which the FRD explicitly defers to a named later phase and which was therefore left unscored rather than failed. ATT-104 ("Selected-property and all-property modes are distinct...") carries no such phase deferral, and Phase 5's own bullet lists "property boundary" as in-scope work for this phase. Originally scored FAIL rather than left untestable, because the FRD's own phase sequencing says this requirement should already be met.

**FIXED, same session, 2026-09-17: `PASS`, scoped to `HOME_ACTIONS`.** Rather than changing `HOME_ACTIONS`'s `requiresProperty: true` registry contract — which would ripple through routing and execution creation, both of which currently assume a Home Actions turn always has exactly one property — the fix adds an explicit, additive all-property *mode* inside the handler itself. A new `isAllPropertyAttentionRequest` gate recognizes a bounded set of explicit framings ("all my properties," "across all my homes," "every property"); when it matches and the homeowner has access to more than one property, `allPropertyHomeActionsResult` aggregates each accessible property's own governed `getHomeActionFeed` call (the SAME canonical pipeline the single-property view already uses — not a shortcut or a lighter recomputation) into a `GROUPED_LIST` sectioned strictly by property.

This directly satisfies both halves of ATT-104: *"labels property on every item"* — each section is titled by the property's own label (reusing the existing `propertyLabel` helper, matching the pattern already used for cross-property session history in `getAskSession`), and every item within it carries that property's own priority/timing/confidence in its `meta`; *"cannot merge records across properties"* — each property's feed keeps its own already-deduplicated item list in its own section; there is no second cross-property dedup/rerank pass, so nothing from two different properties is ever combined into one entry. "No cross-property action retargeting" holds by construction, not by a separate guard: every item's `href` comes directly from `action.primaryCta.href`, which the single-property view already uses unmodified and which is built entirely within that property's own `getHomeActionFeed(property.id, userId)` call — there is no shared "current property" substitution anywhere in the aggregation path that could misdirect an action from one property onto another. The accessible-property list itself reuses the same owned-plus-household-member access boundary `property.service.ts`'s own `getUserProperties` already establishes (without its heavy appliance/health-score hydration, which this attention view has no use for) — the query *is* the access check, so no separate per-property recheck is needed. A property whose feed computation fails is disclosed as unavailable rather than silently dropped or substituted (consistent with T08's XRES-004 discipline elsewhere in this document), and the property list is capped at 10 with an explicit "showing the first N of M" disclosure if a homeowner has more than that.

Scoped deliberately to `HOME_ACTIONS` — the flagship attention aggregator named throughout this document and Phase 0 — not a platform-wide claim that all 5 Phase-5 operations now support all-property mode; they don't. Falls through unchanged to the ordinary single-property read when 0 or 1 property is accessible, so an ordinary single-property homeowner sees no behavior change at all.

**Verification level: 3 new unit tests** in `tests/ask/allPropertyAttentionRequest.test.js` covering the message-detection gate directly (6 recognized phrasings, 3 ordinary single-property questions correctly excluded, a bare "property" mention without "all"/"every" correctly excluded) — all pass, alongside a clean `tsc --noEmit` and the full pre-existing Ask governance/follow-up/view-state suite (59/59 green, no regression). These tests verify **only that the gate recognizes the right phrasings** — that is the full extent of what's independently tested. The aggregation logic itself (`allPropertyHomeActionsResult`, `accessiblePropertiesForAllPropertyAttention`) is **not** independently unit-tested; specifically **untested by anything in this session**:
- **Property isolation** — that two properties' item lists are never merged, deduplicated together, or cross-contaminated in the `GROUPED_LIST` sections.
- **Labels** — that each section's title and each item's property attribution are correct for a homeowner with more than one real property.
- **Authorization** — that a property the homeowner does *not* have access to (not owned, not a household member) never appears in the aggregated list, and that a revoked household membership is reflected on the next ask.
- **Partial-source behavior** — that one property's feed failing genuinely surfaces as the "unavailable" section shape while the others render normally, not a caught exception that silently drops that property or crashes the whole read.
- **Action targeting** — that clicking an item from Property B's section actually navigates to and would act on Property B, not the anchor property or Property A.

This is a real, un-closed verification gap, not just a phrasing detail — this code path composes `getHomeActionFeed`, an already-heavy function with dozens of nested service dependencies (`BuyerAcquisitionService`, `materializeRecommendationsForProperty`, several reconciliation passes) that would require extensive mocking to exercise in isolation without a live database; closing it would need either that mocking investment or a database/browser-backed integration test, neither of which exists this session. **Not** database- or browser-verified.

## T08 — Source becomes unavailable

**Required:** "Item becomes partial/unavailable; no 'all clear' state."

**Verdict: PARTIAL — corrected from an original PASS after external review found a track-level scoring inconsistency.**

**Correction:** the original verdict scored the whole track PASS based on one of five operations (`INTELLIGENCE_ENVELOPE_QUERY`), while its own prose in the same paragraph admitted the flagship operation (`HOME_ACTIONS`) lacks the mechanism. Elsewhere in this same audit series, an identical situation — a requirement genuinely met by some operations in a group and genuinely not met by others — was scored PARTIAL (Financial's F05: true for `REFINANCE_ANALYSIS`/`OWNERSHIP_COSTS`/`SAVINGS_OPPORTUNITIES`, false for `CAPITAL_RESERVE_PLAN`). T08 should have been scored the same way rather than crediting the track with its strongest operation's result alone.

`INTELLIGENCE_ENVELOPE_QUERY` implements the requirement genuinely well. `queryIntelligenceEnvelope`'s result carries a `page.diagnostics` array; when non-empty, the operation returns `status: 'READY_WITH_LIMITATIONS'` with `reasonCode: 'INTELLIGENCE_ENVELOPE_PARTIAL'` and an explicit `BOUNDARY` block naming the exact failing producer and code: `body: page.diagnostics.map((diagnostic) => \`${diagnostic.producerModel}: ${diagnostic.code}\`).join('; ')` (`askOrchestrator.service.ts:6645–6653`). This never collapses into a false "all clear" — the summary's own `tone` is set to `'CAUTION'` whenever diagnostics exist (line 6611), and the partial state is visible alongside whatever data *did* come back, not instead of it.

`HOME_ACTIONS` — the operation named throughout this document and Phase 0 as the flagship attention aggregator, and arguably the operation T08's scenario text is most centrally about, since it's the one that genuinely aggregates multiple producers into one feed — does not implement this requirement. Its `diagnostics` object (`homeActions.service.ts:1330–1354`) tracks counts (`candidateCount`, `surfacedCount`, `duplicateCount`, `suppressedCount`, `emptyStateReason`) but has no per-producer up/down signal comparable to Envelope's. If one underlying producer inside `getHomeActionFeed` fails without throwing, there's no mechanism visible in the diagnostics shape to mark the resulting gap as "partial" the way T08 asks — it would either throw (caught by `homeActionsResult`'s own try/catch into a coarse, honest, but track-wide `UNAVAILABLE`, not a per-item partial state) or silently produce fewer candidates with no visible signal that a source was down. `MAINTENANCE_FORECAST`, `HOME_CHANGE_SUMMARY`, and `INSPECTION_FINDINGS` are each single-source reads from one table, so this scenario doesn't meaningfully apply to them the same way (there's no second producer whose failure could be masked).

Scored PARTIAL: the requirement is genuinely, strongly met by one operation and genuinely absent from the operation most central to the scenario's own framing — the same shape as Financial's F05, scored the same way.

## T09 — Complete underlying work from another surface

**Required:** "Attention item reconciles without duplicate action."

**Verdict: PASS.**

All 5 Phase-5 operations recompute fully live from canonical Prisma state on every call — none of them cache a prior result. `getHomeActionFeed` is called fresh inside `homeActionsResult` with no memoization; `listForecast`/`generateForecast` read/write the live forecast table; `queryIntelligenceEnvelope` reads the live envelope; `listPropertyChanges` and the `prisma.inspectionFinding.findMany` call in `inspectionFindingsResult` are both direct, unmemoized queries. Because a Home Action is *derived* from live canonical state rather than stored as an independent redundant record, completing the underlying work on another surface (e.g., marking a maintenance task done directly) means the next ask simply no longer generates that candidate — there is no separate "attention item" record that could go stale or need a second, duplicate action to clear. This is architectural rather than a specific reconciliation feature, consistent with ATT-110's requirement and with the same live-recompute pattern already confirmed across every other track in this audit series.

## T10 — No actionable items remain

**Required:** "Honest completion/empty state with no forced suggestion."

**Verdict: PASS.**

Every operation in this track has a distinct, honest empty state rather than a generic "nothing to see" or a forced next action: `HOME_ACTIONS` uses `homeActionEmptyCopy(feed.diagnostics.emptyStateReason)`, varying the message by the actual reason (not a single canned string); `HOME_CHANGE_SUMMARY`'s empty state states explicitly, "This covers [sources]. It is not a confirmation that nothing at all happened at this property — only that no material change was recorded in these sources" (`askOrchestrator.service.ts:3416–3417`) — actively guarding against the false-completeness reading; `INSPECTION_FINDINGS` returns "No open confirmed inspection findings" with an optional (not forced) link to the Inspection Hub and an empty `suggestions` array; `MAINTENANCE_FORECAST`'s `NOT_APPLICABLE` branch names the specific reason ("no verified HVAC, roof, or water-heater inventory items"). None of these branches carry a mandatory action — every action offered is a `style: 'PRIMARY'`/`'SECONDARY'` link the homeowner can ignore, not a control the operation requires interacting with to proceed.
