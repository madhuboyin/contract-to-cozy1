# Home Operations & Action Management — Slice 0-8 Launch Review

Companion to [`HOME_OPERATIONS_AND_ACTION_MANAGEMENT_CAPABILITY_AUDIT_AND_IMPLEMENTATION_PLAN.md`](./HOME_OPERATIONS_AND_ACTION_MANAGEMENT_CAPABILITY_AUDIT_AND_IMPLEMENTATION_PLAN.md). Written as part of Slice 9 (portfolio cleanup) to close out the effort with an outcome-based assessment against each slice's own exit criteria, and to consolidate every gap flagged along the way into one place for whoever picks this up next.

## What shipped

A durable `OperationalWorkItem` identity and lifecycle layer (`apps/backend/src/modules/homeOperations/`) now sits underneath Maintenance, Guidance, Project, Inspection Findings, and Status Board — one obligation resolves to one work item across recalculation, regardless of which domain surface it started in. Home's ranked feed (`getPromotedHomeActions`) reads from it; a household write API (assign/watch/transition/duplicate-decision/evidence) now exists over it.

## Consolidated known gaps and follow-ups

In priority order (highest-value first):

1. **Status Board's frontend still runs a second, independent priority computation** (Slice 7 scope decision). This is the one gap that directly contradicts a slice's own exit criterion today. Fixing it means retiring `priorityActionItem`/`PriorityActionHero`/`signalSummary` badges in `StatusBoardClient.tsx` in favor of a reference to Home's own ranking.
2. ~~**Home no longer deep-links to the top Home Event Radar match**~~ — **Fixed** (gap-review backlog item #13): `HomeEventRadarTopMatchCard`, ported into `UnifiedHomeSurface.tsx` as its own standalone widget (mirroring `RefinanceRadarPortfolioCard`'s shape), since Home Event Radar isn't a registered `HOME_ACTION_SOURCE_KIND` and was never going to appear via the ranked-action feed.
3. **Household coordination's larger deliverables are unbuilt** (Slice 8 scope decision): shared calendar/reminders, batch scheduling for low-risk routine work, offline/retry-safe task updates, a real digest wired into the workers app's existing notification infrastructure, operational dashboards/alerting, an accessibility/responsive audit, and a `contractor`/`household` responsibility-state field on `OperationalWorkExecution`.
4. ~~**Recommendation-to-execution work-item continuity gaps**~~ — **Fixed** (gap-review backlog item #14, three gaps): (a) converting a checklist-sourced recommendation into a Maintenance task now reconciles onto its existing recommendation-stage work item instead of forking a new one (`PropertyMaintenanceTask.service.ts`'s `resolveTaskWorkItem`); (b) a Maintenance task promoted to a Project now hands its work item off the same way an Inspection Finding already did (`syncMaintenanceTaskWorkItemForProjectHandoff`); (c) a coverage-shaped Guidance journey handed off to a Project now resolves the correct `INVENTORY_ITEM`/`COVERAGE_ACTION` workKey shape instead of silently no-op'ing (`resolveGuidanceJourneyWorkKey`, deliberately mirroring — not correcting — a separate, still-open recommendation-stage inconsistency in how non-`coverage_gap_resolution` `REGULATED_COVERAGE` journey types pick their subject id).
5. **A handful of dashboard card components likely orphaned by this slice's cleanup** (found during Slice 9 research, not chased per scope decision): `HomeBuyerChecklistCard`, `MyPropertiesCard`, `RecurringMaintenanceCard`, `UpcomingRenewalsCard`, `InsuranceSummaryCard`, `EquityOverviewCard` — each had exactly 2 references (their own definition + the now-deleted dead dashboard that used them). Worth a follow-up grep pass before removing, since "2 references" doesn't rule out a second legitimate caller not caught by this session's targeted checks.
6. **`ProjectIssueCategory` has no dedicated value for `PERMIT`/`FUNCTIONAL` exception types** (Slice 6) — both fall back to `OTHER`. Real, small, deferred as a schema-enum change outside a cleanup slice's scope.

## Product Framework conformance

`assertEveryHomeActionSourceHasAdapter()` (`productFramework/homeActionSourceAdapters.ts`) — the structural self-check that every registered `HomeAction` source kind has a real adapter — passes for all 10 source kinds registered through Slice 5 (including `INSPECTION_FINDING`, added that slice). `capabilityRegistryParity.test.js` (4/4) passes against the currently-committed inventory doc, confirming Home Operations introduced no registry drift (research confirmed neither `/action-plan` nor `/home-operations` is a registered discovery capability at all). While verifying, this slice ran the doc's own regeneration script (`inventory-tool-capabilities.mjs --write`) to check for staleness and found real drift — but it turned out the regenerated output and `capabilityRegistryParity.test.js`'s own fixture *disagree* with each other on a `quote-comparison` capability's label (`"Quote Comparison"` vs `"Service Quote Decision"`), an inconsistency in other, unrelated (Service Price Radar-adjacent) work already in the repo. Regenerating would have swapped one passing state for a newly-failing one, so the doc was left as committed and the discrepancy is flagged here rather than fixed blind.
