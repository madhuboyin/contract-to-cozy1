## Slice 4's implementation

Implements HI-ATT-010 in full. Two parts:

**A. Making the shared Home Operations persistence/use-case layer transaction-aware** (`apps/backend/src/modules/homeOperations/`), required because none of it accepted a transaction client before this slice and no existing caller anywhere wrapped it in `$transaction`:
- `infrastructure/workItemRepository.ts`: new exported `WorkItemDb = typeof prisma | Prisma.TransactionClient` type; every repository function `resolveAndUpsertWorkItem`/`transitionWorkItem` touch takes an optional `db: WorkItemDb = prisma` parameter. `createWorkItem`/`recordWorkEvent`'s P2002-catch-and-refetch is now conditional on `db === prisma` — continuing to query inside an aborted interactive transaction is unsafe, so a transactional caller must catch the propagated error and retry the whole transaction instead (which `booking.service.ts` does, up to 2 attempts).
- `application/resolveWorkItem.usecase.ts` / `application/transitionWorkItem.usecase.ts`: thread `db` through every internal call (including `transitionWorkItem`'s direct `operationalWorkSource.updateMany`/`operationalWorkItem.update` calls, previously hardcoded to the global client). Both gained an optional `onLifecycleEvent` callback (type `WorkItemLifecycleEventCallback`, defined in `infrastructure/workItemChangeEmitter.ts`) — when supplied, the existing inline `emitWorkItemLifecycleChange` call is deferred to the callback instead of firing immediately, so a transactional caller can collect events and only emit them after commit. **Return types are unchanged** (`Promise<OperationalWorkItem>`) — 11 existing callers of `resolveAndUpsertWorkItem` and 14 of `transitionWorkItem` needed zero changes.
- `domain/transitions.ts`: added `SCHEDULED → ACCEPTED` (mirroring the existing `IN_PROJECT → ACCEPTED` precedent — "the thing occupying this item went away, hand it back to the backlog"). `IN_PROGRESS → ACCEPTED` already existed.
- `domain/userGovernance.ts`: both `SCHEDULED → ACCEPTED` and `IN_PROGRESS → ACCEPTED` are excluded from `legalUserWorkItemTransitions` via a new from+to pair check (`EXECUTION_ROLLBACK_PAIRS`) — a homeowner cannot self-serve this rollback; only the booking reconciliation service (via `transitionWorkItem`'s new `eventTypeOverride`) can. `CANDIDATE → ACCEPTED` and `FOLLOW_UP_DUE → ACCEPTED` remain homeowner-legal, since `DOMAIN_MANAGED_STATES`'s target-only exclusion can't express "reachable from some states, not others."
- New `OperationalWorkEventType` value `EXECUTION_CANCELLED`, used via `transitionWorkItem`'s new `eventTypeOverride` field so a booking-cancellation-driven rollback doesn't misrecord as a fresh `WORK_ACCEPTED`.

**B. New `apps/backend/src/services/bookingWorkReconciliation.service.ts`** — origin resolution and reconciliation, called from `booking.service.ts`'s five write methods, each now wrapped in (or extending, for `completeBooking` which already had one) a single `prisma.$transaction`:
- `resolveOriginatingWorkItem`: explicit `originWorkItemId` (new optional `CreateBookingInput` field, server-validated — property match, open state, subject agreement, not already linked to a different booking — never trusted blindly) first; then exact domain provenance only (`guidanceJourneyId` via the existing `resolveGuidanceJourneyWorkKey`, `maintenancePredictionId` via an existing active `OperationalWorkSource` lookup — confirmed no producer sets that today, so this correctly finds nothing rather than being dead code, `priceFinalizationId` by following its own `guidanceJourneyId`); standalone otherwise. `inventoryItemId`, provider, service, category, `executionScopeKey`, and free-text insight fields are never used to select a work item.
- `linkBookingExecution`: the shared, exclusivity-enforcing helper — locks the booking row (`SELECT ... FOR UPDATE`) and rejects linking to a second, different work item, since `OperationalWorkExecution`'s unique index (`[workItemId, executionType, executionEntityId]`) does not by itself prevent one booking from linking to two different work items.
- `reconcileBookingCreated`: reuse transitions a `CANDIDATE` origin to `ACCEPTED`; standalone creates a new `SERVICE_EXECUTION`-obligation item (subject = inventory item if known, else property; occurrence keyed by `booking-${booking.id}` so unrelated bookings never merge) directly at `ACCEPTED`. Both branches record a durable `EXECUTION_LINKED` audit event (booking id, resolution method, matched source, whether standalone) — **read back only for logging/explanation, never for the survives-or-closes decision at cancellation time**, since a classification field is not proof of linkage provenance.
- `reconcileBookingCancelled`: requires **exactly one** linked work item (zero or multiple throws as a reconciliation conflict, never silently resolved). Standalone-vs-reused is decided by whether the item has any other **active** `OperationalWorkSource` with `sourceType != 'BOOKING'` — not by `obligationType` (a classification, not proof) — so both cases share one code path: active independent source → roll back to `ACCEPTED`, clear `scheduleOverrideAt` (preserving the source-derived due window), leave the `BOOKING` execution row as history; no independent source → close with the new `CANCELLED` disposition. Never forces a rollback from `BLOCKED`/`DEFERRED`/completed/verified states.
- `reconcileBookingLifecycle`: `CONFIRMED → SCHEDULED`, `STARTED → IN_PROGRESS`, `COMPLETED → REPORTED_COMPLETE → VERIFIED` (the Booking is authoritative domain evidence — no separate homeowner confirmation gate).

Test coverage: `apps/backend/tests/unit/bookingWorkReconciliation.test.js` (17 tests, in-memory fake `tx` via dependency injection — these functions all take `tx` as an explicit parameter rather than defaulting to the global client, so no `require.cache` override was needed) and `apps/backend/tests/unit/homeOperationsUserGovernanceExecutionRollback.test.js` (5 tests, the homeowner-exclusion guarantee). Writing the reuse-path test caught a real bug: `resolveOriginatingWorkItem`'s "is this candidate already booked" check was querying `findAllWorkItemsLinkedToExecution('BOOKING', candidate.id)`, which treats the *work item's* id as if it were a *booking* id — backwards. Fixed to query executions by `workItemId` directly.

No change to `resolutionCenter.service.ts` or the Fix frontend in this slice — HI-ATT-010 is source-side reconciliation, not the cutover itself.

## Slice 3's implementation

`apps/backend/src/services/orchestration.service.ts`:
- The original plan was an additive loader (Slice 1/2's pattern) producing a richer COVERAGE-kind action for items with a saved `CoverageAnalysis`, relying on the existing dedup machinery (`rankAndDeduplicateHomeActions`'s `coverage-item:<inventoryItemId>` canonical-key grouping, then `linkWorkItemsAndReconcile`'s `workKey` grouping) to pick a winner against the plain orchestration-sourced action. Verified against the actual code that this is unsafe: both dedup passes pick a winner purely by ranking score (safety tier, urgency, confidence, job, actionability, missing-context penalty) then lexicographic action ID — richness of evidence/options/tradeoffs plays no part, so the enriched candidate could lose, and forcing a win by inflating priority/tier would corrupt ranking semantics for an unrelated reason.
- Instead: `adaptOrchestratedActionToHomeAction()` stays synchronous and pure, gaining an optional third parameter (`coverageAnalysis?: { id, confidence, computedAt }`). Its one caller, `getOrchestrationSummary()` (already `async`), batch-loads `CoverageAnalysis` (`status: 'READY'`) for the coverage-gap items in the current action set, reduces to the latest one per item, and passes it through — producing exactly one Home Action per obligation, no competing candidates.
- With an analysis present: `governance.safetyTier` elevates `LOW_CONSEQUENCE` → `MATERIAL_FINANCIAL`; `assumptions`/`options`/`tradeoffs` are synthesized generically (Add protection vs. Self-fund, a coverage/cost tradeoff pair, a computed-at assumption) to satisfy that tier's structural minimums (≥1 assumption, ≥2 options, ≥1 tradeoff per `HomeActionSchema`'s `superRefine`); a second evidence entry references the analysis's id/confidence/computed time, matching Resolution Center's `mapCoverageGapsToInsights` trust block. Without an analysis: byte-for-byte unchanged from before this slice.
- Test coverage: `apps/backend/tests/unit/orchestrationCoverageAnalysisEnrichment.test.js` — no-analysis case unchanged, with-analysis case elevates correctly and round-trips through `HomeActionSchema.parse()`, a non-coverage action is unaffected by the new parameter.

No change to `homeActionSourcePromotion.service.ts`, `resolutionCenter.service.ts`, or the Fix frontend in this slice.

## Slice 2's implementation

`apps/backend/src/services/homeActionSourcePromotion.service.ts`:
- `HomeActionSourceDb`'s optional field group extended with `property` | `document` | `booking` | `replaceRepairAnalysis`.
- New `loadHealthInsightActions(propertyId, db, evaluatedAt?)`: calls `calculateHealthScore()` directly against a raw `db.property.findUnique(...)` (with `inventoryItems`/`warranties` included), `db.document.count(...)`, and `db.booking.findMany(...)` — the same three inputs Resolution Center's `attachHealthScore()` uses, without going through the `userId`-scoped `getPropertyById`. Ports Resolution Center's exact two-branch handling: the aggregate `"Appliances"` factor is recomputed independently from inventory records (so a stale score snapshot can't hide a concrete missing-install-year action), while every other named factor (HVAC age, roof age, per-appliance aging, etc.) is surfaced generically from `calculateHealthScore()`'s own `insights[]`, filtered to the same `HEALTH_INSIGHT_STATUSES` list and matched to an inventory item by the same fuzzy-name logic (including the same deliberate `hvac`/`water heater`/`property` exclusions, so e.g. "HVAC Age" correctly falls back to a factor-detail page rather than mismatching against an arbitrary item named "HVAC"). `SYSTEM`-kind, `LOW_CONSEQUENCE` governance, `PLAN` priority.
- New `loadRepairReplaceDecisionActions(propertyId, db, evaluatedAt?)`: reads `ReplaceRepairAnalysis` (status `READY`) with the same dedupe-by-item logic (prefer `currentMarker === 'CURRENT'`, then most recent `computedAt`) and the same journey-aware/pinned-mode vs. direct-result-page href branching as Resolution Center. `GUIDANCE`-kind, `MATERIAL_FINANCIAL` governance — since that tier requires ≥1 assumption/≥2 options/≥1 tradeoff per the `HomeAction` contract's structural minimums, these are synthesized generically from the analysis's `verdict`/`summary`/`confidence` (Repair vs. Replace options, one favored per verdict; a cost tradeoff per option; a "verdict computed at" assumption) rather than carrying `verdict`/`impactLevel` as new first-class contract fields.
- Both registered in `getPromotedHomeActions()`'s loader list.
- Test coverage: `apps/backend/tests/unit/homeActionHealthInsightPromotion.test.js` (7 tests — appliance aggregate missing-install-year and no-appliances cases, a named factor with fuzzy item matching, the HVAC exclusion-list fallback, a fully-scored property producing zero actions, a missing property record, and the defensive-guard no-throw case) and `apps/backend/tests/unit/homeActionRepairReplacePromotion.test.js` (5 tests — verdict-driven priority/option selection, journey-aware href, item-level dedupe, and the defensive-guard no-throw case).

No change to `resolutionCenter.service.ts`, its API, or the Fix frontend in this slice either.
